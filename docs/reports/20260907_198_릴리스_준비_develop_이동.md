### 📌 작업 개요

main·develop 필수 상태 검사 도입 후 릴리스 워크플로의 보호 브랜치 직접 push가 GH013으로 거절되던 문제를 수정했다. 버전·CHANGELOG·README는 develop 대상 준비 PR에서 검증하고, main 반영도 기존 릴리스 PR의 필수 검사가 끝난 뒤 정상 병합하도록 전환했다.

중단된 릴리스 PR #197을 이어갈 수 있도록 v0.1.11 릴리스 파일과 복구 절차도 함께 반영했다.

### 🔍 문제 분석

기존 워크플로는 develop→main PR의 검사가 끝난 뒤 다음 순서로 보호 브랜치를 직접 변경했다.

1. 버전·CHANGELOG 변경 커밋을 develop에 직접 push
2. develop을 로컬에서 main에 병합한 뒤 main에 직접 push
3. 병합 결과에 버전 태그 생성

필수 상태 검사는 검사받은 커밋 SHA에만 유효하다. 워크플로가 검사 이후 만든 새 커밋에는 빌드·유닛·E2E 결과가 없으므로 develop push가 GH013으로 거절됐고, 뒤의 main 병합·태그·배포도 실행되지 않았다.

### ✅ 구현 내용

#### 릴리스 준비를 develop PR로 전환

- **파일**: `.github/workflows/PROJECT-COMMON-RELEASE-CHANGELOG.yaml`
- **변경 내용**: 버전·CHANGELOG·README 변경을 `release-prep-<릴리스 PR 번호>` 브랜치에 커밋하고 develop 대상 PR로 생성한다.
- **이유**: 생성된 릴리스 커밋도 빌드·유닛·E2E 필수 검사를 받은 뒤 보호 브랜치에 들어가게 한다.

준비 PR의 필수 검사가 등록될 때까지 기다린 뒤 모두 통과하면 일반 merge로 병합한다. 보호 규칙 우회 옵션과 main·develop 직접 push는 사용하지 않는다.

#### 준비된 develop을 main에 정상 병합

- **파일**: `.github/workflows/PROJECT-COMMON-RELEASE-CHANGELOG.yaml`
- **변경 내용**: 준비 PR 병합으로 head SHA가 갱신된 원래 develop→main PR의 필수 검사를 다시 기다린 후 예상 head SHA를 지정해 병합한다.
- **이유**: 검사 중 develop이 다시 변경되는 경쟁 상태와 검사받지 않은 커밋의 병합을 막는다.

#### 재실행 중복 방지

- 열린 릴리스 준비 PR이 있으면 새 버전을 만들지 않고 기존 PR의 검사·병합부터 이어간다.
- develop 버전이 main보다 이미 앞서 있으면 CHANGELOG 최신 버전과 README 표기를 확인한 뒤 준비 완료 상태로 처리한다.
- main의 `version.yml` 변경에서 태그를 만들며, 같은 태그가 있으면 종료한다.

#### v0.1.11 릴리스 복구 자료 반영

- **파일**: `version.yml`, `package.json`, `CHANGELOG.json`, `CHANGELOG.md`, `README.md`
- **변경 내용**: 실패한 PR #197에서 확정한 버전을 0.1.11로 올리고 당시 릴리스 노트를 반영했다.
- **이유**: 새 워크플로가 main에 들어가기 전에 열린 PR #197은 새 준비 흐름을 실행할 수 없으므로, 이번 변경을 develop에 병합해 검사를 다시 받게 한다.

#### 복구 절차 기록

- **파일**: `docs/issues/20260907_설정_릴리스_준비를_develop으로_이동.md`
- **변경 내용**: 변경 PR→develop 병합, PR #197 재검사·main 병합, v0.1.11 태그 확인 순서를 기록했다.

### 🧭 결정 기록 (ADR)

#### 보호 브랜치 예외 대신 준비 PR 사용

- **문제**: 릴리스 봇이 새로 만든 커밋에는 필수 검사 결과가 없어 직접 push가 거절된다.
- **선택**: 릴리스 생성물을 별도 브랜치에 커밋하고 develop 대상 PR의 필수 검사를 통과시킨다.
- **대안**:
  - 봇을 ruleset 우회 대상에 추가 — 검사 없는 변경도 들어갈 수 있어 보호 규칙의 의미가 약해진다.
  - main에서 릴리스 파일을 다시 생성 — develop과 main의 내용이 달라지고 역동기화가 필요하다.
- **트레이드오프**: 릴리스마다 준비 PR과 필수 검사 한 회가 추가된다.
- ⭐ **볼트 승격 권장** — 다른 저장소의 공용 릴리스 워크플로에도 영향을 주는 운영 결정이다.

#### 태그 생성을 main의 version.yml push로 분리

- **문제**: 전환 전에 열린 PR #197은 새 pull request 워크플로를 다시 실행할 수 없다.
- **선택**: `version.yml`이 포함된 main push에서 현재 버전 태그를 생성한다.
- **대안**: PR #197 병합 뒤 태그를 수동 생성 — 이번 복구에는 쓸 수 있지만 이후 릴리스 경로가 둘로 나뉜다.
- **트레이드오프**: main에서 version.yml을 수동 변경해도 태그 job이 실행되지만, 기존 태그 검사가 중복 생성을 막는다.
- ⭐ **볼트 승격 권장** — 릴리스와 태그의 기준 이벤트를 정하는 운영 결정이다.

### 🔧 주요 변경사항 상세

릴리스 워크플로는 기존 버전 관리자, CHANGELOG 관리자, provider 사다리를 그대로 재사용한다. 새 로직은 GitHub CLI로 준비 PR을 만들고 `gh pr checks --required --watch`로 ruleset의 필수 검사를 조회하므로 검사 이름을 워크플로에 중복 정의하지 않는다.

README 버전도 준비 커밋에 포함한다. main push 뒤 실행되는 README 워크플로는 변경사항이 없으므로 main 직접 push와 develop 역동기화 경로를 타지 않는다. 기존 버전 관리 안전망 역시 `version.yml` 변경을 릴리스 병합으로 감지해 추가 버전 증가를 건너뛴다.
