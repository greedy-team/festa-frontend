### 📌 작업 개요

통합 검색에서 타입 칩(아티스트·학교·축제)으로 결과를 좁혔을 때, 그 타입 매치가 0건이어도 헤더가 "N건"으로 뜨고 "검색 결과가 없습니다." 안내가 나오지 않던 문제 수정.

`src/app/search/page.tsx`가 헤더 카운트와 빈 상태 판정을 모두 `counts.all`로 하던 것을, 헤더는 선택된 타입의 count로, 빈 상태는 실제 렌더된 배열 기준으로 바꿨다. 재현 e2e 테스트를 추가하고, 리뷰 반영으로 그 테스트를 데이터 값 비의존 방식으로 재작성했다.

**보고서 파일**: `docs/reports/20260902_145_검색_타입_칩_0건_헤더_빈상태_정합.md`

### 🔍 문제 분석

`counts.all`은 아티스트·학교·축제 세 도메인 매치 수의 합이라 타입 필터와 무관하다. 기존 코드는 타입과 상관없이 이 값 하나로 헤더 수치와 빈 상태를 판단했다.

- 헤더: `“{q}” 검색 결과 {data.counts.all}건`
- 빈 상태: `!data.counts.all`일 때만 "검색 결과가 없습니다." 렌더

그래서 특정 타입으로 좁혔는데 그 타입 매치가 0건이어도, 다른 타입에 매치가 있으면 `counts.all > 0`이라 헤더가 "1건" 등으로 뜨고 빈 안내도 안 나왔다. 화면에는 아무 카드도 없는데 헤더만 숫자가 찍히는 상태.

부수 증상: `type=HOST`로 좁혀 학교 매치가 2건인데 실제 렌더된 행은 1건인 경우처럼, 헤더 수치와 화면이 어긋나는 케이스도 같은 원인이었다.

### ✅ 구현 내용

#### 헤더 카운트를 선택 타입 기준으로 분기

- **파일**: `src/app/search/page.tsx`
- **변경 내용**: `SearchType`(`ALL` 제외) → `SearchCounts` 키를 매핑하는 `COUNT_KEY` 맵 추가. `resultCount = type === "ALL" ? data.counts.all : data.counts[COUNT_KEY[type]]`
- **이유**: 타입으로 좁히면 그 타입 count만 봐야 헤더 수치와 실제 그려진 섹션이 일치한다

#### 빈 상태 판정을 렌더된 배열 기준으로 변경

- **파일**: `src/app/search/page.tsx`
- **변경 내용**: `!data.counts.all` → `isEmpty = !data.artists.length && !data.hosts.length && !data.festivals.length`
- **이유**: count가 아니라 화면에 실제 그려진 결과를 기준으로 두면, 헤더 수치와 빈 안내가 구조적으로 어긋날 수 없다

#### 재현 e2e 테스트 추가

- **파일**: `e2e/search.spec.ts`
- **변경 내용**: 타입 칩으로 좁혀 결과가 0건일 때 헤더 "0건" + "검색 결과가 없습니다."가 뜨는지 검증하는 테스트 추가
- **이유**: 수정 전 코드에서 두 단언 모두 실패하는 회귀 테스트로 고정

#### (리뷰 반영) e2e 테스트를 데이터 값 비의존 방식으로 재작성

- **파일**: `e2e/search.spec.ts`
- **변경 내용**: 초안은 "싸이"라는 검색어를 하드코딩하고 그것이 fixture에서 아티스트로만 존재한다는 전제에 의존했다. 이 스위트의 "데이터 값을 하드코딩하지 않는다" 방침에서 벗어나고, fixture에 싸이 들어간 학교·축제가 추가되면 거짓 실패한다. 아래 방식으로 교체:
  1. `/artists` 목록 첫 행 이름을 실행 시점에 읽어 검색어로 사용 (아티스트로는 반드시 매치됨)
  2. `/search?q=<이름>`(ALL) 응답에서 섹션이 안 그려진 타입 = 그 타입 0건
  3. 그 타입 칩(`a[href*="type=..."]`)으로 이동. 칩 라벨 "학교"가 사이트에서 유일해 HOST 우선, 그마저 매치되면 FESTIVAL
  4. 헤더 "0건" + 빈 안내 단언. 세 타입 모두 매치되는 경우는 `test.skip`으로 빠짐
- **이유**: 검색어·타입을 고정하지 않고 같은 회귀를 잡기 위함

#### (리뷰 반영) COUNT_KEY 주석에 이원 판정 기준 설명 추가

- **파일**: `src/app/search/page.tsx`
- **변경 내용**: 헤더는 count, 빈 상태는 배열 길이로 판정 기준이 둘이지만, 백엔드가 선택 타입 count를 `list.size()`로 내고 검색 쿼리 세 개 모두 LIMIT이 없어 현재 계약에선 항상 같은 값이라는 점, 어긋나려면 백엔드 결함이 필요하다는 점을 주석에 명시
- **이유**: 나중에 읽는 사람이 이원 기준을 버그로 오해하지 않도록

### 🧭 결정 기록 (ADR)

#### 빈 상태 판정을 count가 아니라 렌더된 배열로

- **문제**: 헤더 수치와 빈 안내가 서로 다른 근거(둘 다 `counts.all`이었다가, 헤더만 타입별 count로)로 갈리면 다시 어긋날 여지가 남는다
- **선택**: 빈 상태는 실제 렌더 조건(`artists`·`hosts`·`festivals` 배열 길이)과 동일한 값으로 판정
- **대안**: 빈 상태도 `!counts[COUNT_KEY[type]]`로 맞추기 — 현재 계약에선 동일하지만, count와 배열이 다른 값이 될 여지(백엔드가 count에 LIMIT을 걸는 등)를 남긴다
- **트레이드오프**: 판정 기준이 헤더(count)와 빈 상태(배열)로 둘이 된다. 현재 계약에선 항상 일치하지만 주석으로 근거를 남겨야 한다
- 되돌리기 쉬운 프론트 내부 결정이라 볼트 승격 대상은 아님

### 🔧 주요 변경사항 상세

#### src/app/search/page.tsx

`COUNT_KEY` 맵으로 `ARTIST → "artist"`, `HOST → "host"`, `FESTIVAL → "festival"` 매핑. `res.data` 이후 `resultCount`와 `isEmpty`를 계산해 헤더 문구와 빈 안내 조건에 사용. 결과 섹션(아티스트·학교·축제) 렌더 조건은 기존대로 각 배열 길이를 그대로 쓴다.

**특이사항**:
- `counts.all`은 백엔드 계약상 타입 무관 합계다 (`festa-backend#108`에서 확정, PR #141 리뷰 라인 코멘트로 남기고 approve됨)
- 백엔드 응답의 대상별 count(`counts.host` 등)는 이미 정상이라 그대로 사용. 프론트 전용 수정이다

#### e2e/search.spec.ts

`/artists` 첫 행 → 검색어 확보 → ALL 검색 → 안 그려진 타입 칩 클릭 → 0건·빈 안내 단언. 칩 선택은 `a[href*="type=HOST"]`처럼 href 부분 매칭으로 nav·footer의 동명 링크와 충돌을 피한다.

**특이사항**:
- e2e는 `NEXT_PUBLIC_API_MOCKING=true`로 mock fixture 데이터에서 돈다. "첫 아티스트 이름이 학교·축제명에 없다"는 약한 전제는 남지만, fixture가 그 조건을 깨면 `test.skip`으로 빠져 거짓 실패는 나지 않는다
