# 진행 중인 축제는 D-day를 D-DAY로 고정 표기

## 📌 작업 개요

홈 히어로·검색 결과 축제 행·축제 상세 히어로의 D-day가 시작일 기준으로만 계산돼, 이미
시작한 축제는 "D+2"처럼 시작일로부터 지난 일수로 떴다. 진행 중인 축제는 세 화면 모두
날짜와 무관하게 "D-DAY"로 고정한다.

관련 이슈: #218

## 🎯 구현 목표

- 진행 중(시작일 ~ 종료일 사이)인 축제는 며칠째든 D-day를 "D-DAY"로 고정 표기
- 시작 전 축제는 기존 시작일 기준 `D-N` 표기 유지
- 홈 히어로·검색 결과 축제 행·축제 상세 히어로, 세 화면 모두 같은 계산을 쓸 것

## ✅ 구현 내용

### D-day 계산 함수에 진행 중 분기 추가

- 파일: `src/lib/festivalDate.ts`
- 변경 내용: `dDay(startDate, today?)` → `dDay(startDate, endDate, today?)`로 시그니처
  변경. `festivalStatus(startDate, endDate, today)`가 `"ONGOING"`이면 곧바로 `"D-DAY"`를
  반환하고, 그 외(시작 전·종료)에는 기존과 같은 방식(시작일까지 남은 일수)으로 계산한다.
- 이유: 진행 중 여부 판정을 새로 만들지 않고 기존 `festivalStatus`를 재사용했다 —
  같은 "오늘이 시작일~종료일 사이인가"를 두 곳에서 따로 판정하면 언젠가 갈린다.

  처음에는 진행 중일 때 "종료일까지 남은 일수"(`D-2` → `D-1` → `D-DAY`)로 구현했다가,
  요청이 "진행 중인 3일 다 D-DAY로 보이게"였음을 뒤늦게 확인하고 되돌렸다 — 아래
  "테스트 및 검증"의 유닛테스트가 최종적으로 이 동작(며칠째든 D-DAY)만 남아 있다.

### 호출부 두 곳에 endDate 전달

- 파일: `src/features/home/components/HeroPanel.tsx`,
  `src/features/search/components/FestivalResultRow.tsx`
- 변경 내용: `dDay(startDate)` → `dDay(startDate, endDate)`. 두 컴포넌트 모두 `endDate`를
  이미 props로 받고 있어 destructure만 그대로 두고 호출부만 고쳤다.

### 축제 상세 히어로도 서버 dday 대신 프론트 계산으로 전환

- 파일: `src/features/festivals/components/FestivalHero.tsx`,
  `src/features/festivals/types.ts`
- 변경 내용: `<Badge>{formatDday(dday)}</Badge>`(서버가 내려주는 `FestivalDetail.dday`를
  포맷만 함) → `<Badge>{dDay(startDate, endDate)}</Badge>`. `dday` destructure와
  `formatDday` import를 제거했다. `types.ts`의 `dday` 필드 주석을 "다시 계산하지 않는다"에서
  실제 동작(화면은 다시 계산한다)에 맞게 갱신했다.
- 이유: mock 핸들러(`daysUntil(f.startDate)`)를 보면 서버의 `dday`도 시작일 기준이라 진행
  중이면 똑같이 "D+N"이 된다. 홈·검색을 고쳐도 상세만 남으면 같은 축제가 화면마다 다르게
  보인다.

## 🧭 결정 기록 (ADR)

### 진행 중에는 종료일까지 남은 일수가 아니라 D-DAY로 고정

- 문제: "그 날까지 D-day로"라는 요청을 처음엔 "종료일까지 카운트다운"(`D-2`→`D-1`→`D-DAY`)
  으로 해석해 구현했다. 확인차 "09.09~09.11이면 세 날 다 D-DAY로 뜨는 거죠?"라고 물었더니
  "그렇다"였다 — 카운트다운이 아니라 **진행 중인 동안은 계속 D-DAY**가 맞는 요구였다.
- 선택: `festivalStatus`가 `ONGOING`이면 날짜 계산 없이 즉시 `"D-DAY"`를 반환한다.
- 이유: 사용자가 알고 싶은 건 "며칠 남았나"가 아니라 "오늘이 축제 날인가"였다. 진행 중
  하루하루가 전부 그 축제의 "당일"이라는 뜻으로 보는 것이 더 맞다.
- 트레이드오프: 3일짜리 축제와 10일짜리 축제가 진행 중엔 똑같이 "D-DAY"로 보여
  구분되지 않는다 — 정보량이 준다. 축제 상세에는 시작~종료일 자체가 아래 별도 줄로
  나와 있어(`dateRangeWithYear`) 정확한 기간은 거기서 확인할 수 있다.

### 종료된 축제는 이번 범위에서 제외하고 기존 동작(D+N, 시작일 기준) 유지

- 문제: `dDay`가 세 상태(시작 전 / 진행 중 / 종료) 중 진행 중만 다루면, 종료된 축제의
  표기를 어떻게 할지도 같이 정해야 하는가?
- 선택: 종료된 축제는 손대지 않는다. `today > endDate`면 기존처럼 시작일 기준 `D+N`을
  그대로 낸다.
- 이유: 이슈(#218)가 "진행 중"만 지목했고, 종료된 축제의 표기는 DEC-0059가 남긴 별개의
  미해결 항목("이미 지난 축제의 디데이를 어떻게 표기할지 논의 기록 없음")이라 범위를
  넓히면 별도 논의 없이 값을 정하게 된다. 실제로 `getUpcomingFestivals()`가 ENDED를
  걸러 홈 히어로엔 등장하지 않고, 검색 결과에 종료 축제가 뜨는 경우(과거 라인업 아카이브)의
  적절한 표기는 이번 이슈와 다른 질문이다.
- 트레이드오프: 검색에서 아주 오래전에 끝난 축제는 여전히 `D+380` 같은 큰 값을 보일 수
  있다 — 별도 이슈감이다.

### 축제 상세는 예외적으로 서버 dday를 신뢰하지 않는다

- 문제: 이 저장소는 "서버가 계산해 내려주는 dday는 다시 계산하지 않고 포맷만 한다"는
  관례를 갖고 있다(`festivals/types.ts`, 호스트·아티스트의 `dday`도 같은 관례). 이번 요청은
  그 관례를 깨고 프론트에서 다시 계산하라는 것이다.
- 선택: 축제 상세 히어로만 예외로 두고 `dDay(startDate, endDate)`로 프론트에서 계산한다.
  호스트 상세의 `upcomingFestivals[].dday`(공연일 기준, 진행 중 개념 자체가 옅음)와
  아티스트의 `dday`(공연 하루짜리 이벤트)는 그대로 서버 값을 쓴다 — 이 이슈(#218)가
  지목한 건 "여러 날짜에 걸친 축제"의 진행 중 표기뿐이다.
- 이유: 백엔드의 `dday` 계산 로직을 이 저장소에서 바꿀 수 없다. 같은 축제가 홈·검색·상세
  세 화면에서 다르게 보이는 것보다, 화면 쪽에서 이미 검증된 계산(`dDay`)으로 통일하는
  쪽을 택했다.
- 트레이드오프: "서버 dday는 다시 계산하지 않는다"는 관례가 축제 상세에서만 깨진다.
  나중에 백엔드가 dday 계산을 이 규칙에 맞게 고치면, 이 프론트 계산은 중복이 되고
  다시 되돌릴 수 있다 — 그때까지는 이 파일의 주석이 이유를 남긴다.

## 🔧 주요 변경사항 상세

### festivalDate.ts

```
if festivalStatus(startDate, endDate, today) === "ONGOING": return "D-DAY"
else: days = 시작일까지 남은 일수 (기존과 동일); return formatDday(days)
```

`festivalStatus`가 이미 `today < startDate` → UPCOMING, `today > endDate` → ENDED,
그 외 ONGOING으로 판정하므로 `dDay`는 ONGOING 여부만 보고 조기 반환한다.

특이사항:
- 시그니처가 `(startDate, today?)`에서 `(startDate, endDate, today?)`로 바뀌어 위치 인자
  순서가 달라졌다. 호출부가 3곳뿐이라 전수 수정했고, 테스트도 함께 갱신했다.
- `GET /hosts/{id}`의 `upcomingFestivals[].dday`, 아티스트 예정 공연의 `dday`처럼 서버가
  이미 계산해 내려주는 값은 그대로 `formatDday`로 포맷만 하며 이번 변경의 영향 밖이다.
  축제 상세의 `dday`만 예외적으로 프론트 계산(`dDay`)으로 바꿨다 — 위 ADR 참고.

  검증했다. 세 화면 모두 같은 `dDay` 함수를 호출하므로 그 유닛테스트가 세 화면의 로직을

  재계산은 그때 되돌릴 수 있다(위 ADR).
