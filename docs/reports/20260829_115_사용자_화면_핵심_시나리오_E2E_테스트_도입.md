### 📌 작업 개요

유닛테스트(#100)는 순수 함수 단위만 검증하고, 실제 브라우저에서 페이지 이동·검색·폼 제출 같은 사용자 흐름은 검증하지 못했다. Playwright로 로그인이 필요 없는 사용자 화면의 핵심 시나리오 6건을 E2E로 커버했다.

### 🎯 구현 목표

- Playwright 도입(최소 구성)
- 사용자 화면 핵심 시나리오 커버: 홈→축제 상세, 축제 목록 정렬, 아티스트 검색, 아티스트 상세→예정 공연 이동, 통합 검색, 주최 상세→축제 이력
- CI에서 PR마다 자동 실행

### ✅ 구현 내용

#### Playwright 도입
- **파일**: `playwright.config.ts`(신규), `package.json`
- **변경 내용**: `@playwright/test`만 devDependency로 추가하고 `test:e2e` 스크립트(`playwright test`)를 등록. `testDir: "./e2e"`, chromium 프로젝트 하나만 사용
- **포트를 3100으로 분리**: `pnpm dev`나 다른 로컬 서비스가 3000을 쓰고 있을 수 있는데, `reuseExistingServer`가 그 무관한 서버에 그대로 붙어버리는 사고를 실제로 겪었다(아래 참고사항). 3100으로 분리해 재발을 막았다

#### E2E 시나리오 6건
- **파일**: `e2e/home-to-festival-detail.spec.ts`, `festivals-sort.spec.ts`, `artists-search.spec.ts`, `artist-detail-upcoming-show.spec.ts`, `search.spec.ts`, `host-history.spec.ts`
- **변경 내용**:
  - 홈 → 축제 상세: 히어로/최근 등록 카드 링크 클릭 → 상세 페이지 이동·`h1` 노출 확인
  - 축제 목록 정렬: `SortDropdown`으로 정렬 변경 → URL에 `sort` 반영 확인 (검색 pill은 아직 표시 전용이라 시나리오에서 뺐다 — 아래 참고사항)
  - 아티스트 검색: 목록 첫 아티스트 이름 일부를 검색어로 써서 결과가 좁혀지는지 확인 (하드코딩된 검색어 없음)
  - 아티스트 상세 → 예정 공연: 아티스트를 순회하며 예정 공연이 있는 첫 케이스를 찾아 카드 클릭 → 축제 상세 이동 확인. 없으면 스킵
  - 통합 검색(`/search`): 검색어 입력 → 결과 URL 확인
  - 주최 상세 → 축제 이력: 축제 상세 → 주최 상세 → "전체 보기" → `/hosts/{id}/history` 이동 확인
- **원칙**: 특정 축제·아티스트 이름 같은 데이터 값이 아니라 URL 패턴·요소 존재 여부처럼 데이터(목/실제 어느 쪽이든)가 바뀌어도 흔들리지 않는 것만 검증

#### CI 워크플로우 추가
- **파일**: `.github/workflows/FESTA-E2E.yaml`(신규)
- **변경 내용**: PR(`main`/`develop` 대상)마다 `pnpm exec playwright install --with-deps chromium` 후 `pnpm test:e2e` 실행. `NEXT_PUBLIC_API_MOCKING=true`를 워크플로우 env로 강제 — CI엔 실제 백엔드가 없어서 서버 사이드 MSW(`instrumentation.ts`)로 앱을 띄운다
- 기존 빌드 검증(`PROJECT-REACT-CI.yaml`)에 합치지 않고 분리 — `PROJECT-` 접두어 파일은 `npx projectops` 업데이트 시 덮어써지기 때문(#100과 같은 이유)

### 🧭 결정 기록 (ADR)

#### E2E 전용 포트를 3000이 아닌 3100으로 분리
- **문제**: 로컬에서 `reuseExistingServer: true`(비-CI 기본값)로 처음 돌렸더니, 이 머신의 3000번 포트를 이미 다른 서버(무관한 Docker 컨테이너)가 쓰고 있어서 Playwright가 그 서버에 그대로 붙어버렸다. 홈페이지 스크린샷을 찍어보고 나서야 우리 앱이 아니라는 걸 알았다
- **선택**: baseURL·webServer 포트를 3100으로 고정
- **트레이드오프**: 다른 프로젝트가 하필 3100도 쓰고 있으면 같은 문제가 재발할 수 있다. 완전한 해법은 아니지만 가장 흔한 충돌(3000)은 피한다

#### 데이터 값이 아니라 구조를 검증
- **문제**: 실제 데이터를 쓰는 E2E(로컬은 MSW 목, CI도 MSW 목으로 고정)에서 "축제명이 OO인지" 같은 값 검증은 데이터가 바뀌면 테스트가 함께 깨진다
- **선택**: URL 패턴(`/festivals/\d+`), 요소 존재 여부, "검색어를 넣으면 결과가 그 검색어를 포함한다" 같은 구조적 불변식만 검증
- **트레이드오프**: 특정 데이터 버그(예: 특정 축제명이 잘못 표시됨)는 이 테스트로 못 잡는다. 그건 유닛테스트나 수동 QA의 몫으로 남긴다

#### 축제 목록 시나리오를 "검색"이 아니라 "정렬"로 수정
- **문제**: 처음엔 "축제 목록 검색·필터"로 시나리오를 잡았는데, 실제로 `/festivals`의 `SearchPill`은 아직 `aria-hidden`인 표시 전용 컴포넌트였다(실제 검색 동작 미구현)
- **선택**: 시나리오를 실제로 조작 가능한 `SortDropdown`(GET 폼 + native select) 검증으로 바꿨다
- **결과**: 검색 UI가 실제로 붙으면 이 파일에 케이스를 추가한다

### 🔍 리뷰 반영

PR #118 리뷰(EM-H20)에서 실질적인 지적 8건이 나왔고 전부 반영했다.

- **`h1` 존재만 확인하던 검증이 사실상 항상 통과함** — `error.tsx`·`not-found.tsx`도 둘 다 `h1`을 그려서, 상세 페이지가 500·404여도 검증이 통과했다. 4개 스펙(home-to-festival-detail·festivals-sort·host-history·artist-detail-upcoming-show)에서 클릭 전에 카드 이름을 읽어두고, 이동 후 `h1` **텍스트**가 그 이름과 일치하는지 확인하도록 바꿨다
- **`artist-detail-upcoming-show`의 스킵이 진짜 실패를 가릴 수 있었음** — `evaluateAll`은 Playwright 자동 대기가 안 걸려서, 목록이 아직 안 그려진 상태에서 부르면 0개가 나와 "예정 공연 없음"과 "목록 렌더링 자체가 깨짐"이 똑같이 스킵으로 끝났다. 렌더 대기를 먼저 넣고, 그래도 0개면 스킵이 아니라 실패로 처리하도록 바꿨다
- **CI 리포터가 `github` 하나뿐이라 `playwright-report/`가 안 만들어짐** — 실패 시 업로드하려던 트레이스·스크린샷이 애초에 없었다. `html` 리포터를 같이 켰다
- **`SortDropdown`의 하이드레이션 레이스 가능성** — 제출 버튼 없이 `onChange` → `requestSubmit()`으로만 제출되는데, 하이드레이션 전에 값이 바뀌면 네비게이션이 안 일어날 수 있다. `toHaveURL`에 15초 타임아웃 여유를 줬다
- **`/search` 테스트가 URL만 봐서 API 실패와 구분이 안 됨** — 실패해도 같은 URL에서 "불러오지 못했습니다"를 그리는데 URL은 똑같다. 결과 헤딩("검색 결과 N건") 노출까지 확인하도록 추가
- **`encodeURIComponent`가 이스케이프하지 않는 문자로 인한 정규식 파손 위험** — `( ) . * !`가 포함된 검색어(예: "(여자)아이들")에서 정규식이 깨질 수 있었다. `new URL(page.url()).searchParams.get("q")`로 실제 값을 비교하는 방식으로 변경
- **로컬 `.env.local`과 CI가 다른 데이터로 테스트될 수 있음** — `pnpm build`가 `.env.local`을 읽어서, 실제 백엔드를 보게 설정해둔 사람이 `pnpm test:e2e`를 돌리면 CI와 다른 결과가 나온다. `webServer.env`로 `NEXT_PUBLIC_API_MOCKING=true`를 고정하고, `FESTA-E2E.yaml`의 중복 `env:` 블록은 지웠다(같은 규칙을 두 곳에 적지 않는다)

리뷰어가 승인하며 마크업까지 직접 대조 검증했다(히어로 `h2`·카드류 `h3`가 전부 `{name}`인지, 호스트 링크 텍스트 파싱이 원문과 맞는지 등). 추가로 "Rulesets에 `E2E 테스트`도 required status check로 걸면 좋겠다"는 제안이 있었는데, 이건 저장소 Settings 변경이라 이 PR 범위 밖으로 남겼다.

### 📌 참고사항

- 이 작업 중 실제로 겪은 사고: 로컬 3000번 포트에 이미 무관한 서버가 떠 있어서, 첫 실행에서 E2E가 우리 앱이 아닌 그 서버를 대상으로 "통과"할 뻔했다(스크린샷으로 확인하고 나서야 발견). 포트를 3100으로 분리해서 막았다 — 팀원 로컬 환경에서도 3100이 겹치면 `playwright.config.ts`의 `PORT` 상수만 바꾸면 된다
