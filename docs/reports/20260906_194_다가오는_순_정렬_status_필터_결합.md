# "다가오는 순" 정렬이 오래된순으로 동작하는 문제 수정

### 📌 작업 개요

/festivals의 정렬 옵션 "다가오는 순"이 실제로는 가장 오래된 축제부터 보여주던 문제를 수정했다. "다가오는 순" 선택 시 `sort=UPCOMING`에 더해 `status=UPCOMING`을 함께 전송하도록 바꿨다. 백엔드 변경은 없다.

### 🔍 문제 분석

"다가오는 순"은 `sort=UPCOMING` 하나만 전송했다. 그런데 `sort`와 `status`는 이름만 겹칠 뿐 다른 축이다.

- `sort=UPCOMING` — 개최일 오름차순 정렬만 한다. 지난 축제를 걸러내지 않는다.
- `status=UPCOMING` — KST 오늘 기준 시작일이 오늘보다 뒤인 축제만 남긴다.

프론트는 `status`를 아예 안 보내고 있었다. `getFestivals`의 파라미터 타입에 `status`가 없었다. 그 결과 "다가오는 순"은 전체 축제를 개최일 오름차순으로 정렬만 해서, 가장 오래된 축제가 첫 화면에 왔다.

지금 데이터로는 증상이 드러나지 않는다. DB의 축제가 대부분 현재~미래라 오름차순이 사실상 다가오는 순처럼 보인다. 크롤러 백필(2023~2025)이 발행되면 "다가오는 순"의 첫 화면이 과거 축제로 채워진다.

`/hosts/[id]/history` 화면은 같은 `sort=UPCOMING`을 "오래된순"으로 부른다. 과거 축제만 있는 화면이라 오름차순이 곧 오래된순이고, 그쪽 라벨은 맞다. 틀린 쪽은 /festivals다.

### ✅ 구현 내용

#### getFestivals에 status 파라미터 추가
- **파일**: `src/features/festivals/api.ts`
- **변경 내용**: `Params`에 `status?: FestivalStatus` 추가, 값이 있을 때만 `params.set("status", status)`
- **이유**: 백엔드와 MSW 목이 이미 `status`를 받아 필터하는데 프론트만 안 쓰고 있었다

#### FestivalStatus 타입 re-export
- **파일**: `src/features/festivals/types.ts`
- **변경 내용**: `export type { FestivalStatus } from "@/lib/festivalDate";` 한 줄 추가
- **이유**: `FestivalStatus`는 판정 함수 `festivalStatus()`와 함께 `festivalDate.ts`에 이미 정의돼 있다. 목록 파라미터 타입이 쓸 수 있게 다시 내보내기만 하고, 재정의하지 않는다

#### "다가오는 순"일 때 status 파생
- **파일**: `src/app/festivals/page.tsx`
- **변경 내용**: `sort === "UPCOMING"`이면 `status = "UPCOMING"`을 파생해 두 `getFestivals` 호출(초기 + 페이지 상한 클램프 재조회)에 전달
- **이유**: status를 URL 스키마에 새로 넣지 않고 서버 컴포넌트에서 `sort`로부터 파생한다. 드롭다운은 지금처럼 `sort`만 토글한다. 이력 화면은 같은 sort를 "오래된순"으로 쓰므로 이 파생 로직을 두지 않는다

#### 회귀 테스트 추가
- **파일**: `e2e/festivals-sort.spec.ts`
- **변경 내용**: "다가오는 순"에서 픽스처의 가장 오래된(확정 과거) 축제가 목록에 없는지 검증하는 테스트 1건 추가

### 🧭 결정 기록 (ADR)

#### status를 URL에 넣지 않고 sort에서 파생

- **문제**: "다가오는 순"이 `status=UPCOMING`을 함께 보내야 하는데, `status`는 URL 파라미터에 없다
- **선택**: `festivals/page.tsx` 서버 컴포넌트에서 `sort === "UPCOMING"`일 때 `status`를 파생한다. URL은 `?sort=UPCOMING` 그대로, `SortDropdown`도 그대로
- **대안**:
  - URL에 `status`를 별도 파라미터로 추가 — 드롭다운·검색폼·페이지네이션이 전부 `status`를 실어 나르게 고쳐야 한다. "다가오는 순"과 `status=UPCOMING`은 항상 1:1이라 두 값을 따로 둘 이유가 없다
  - `SortDropdown`이 `status`까지 함께 제출 — 컴포넌트가 정렬 외의 필터 축을 알게 되고, 이력 화면에서는 그 동작이 틀리다
- **트레이드오프**: `sort`와 `status`의 결합이 페이지 컴포넌트 안에 암묵적으로 산다. 나중에 "다가오는 순"에 ONGOING을 포함하는 등 조합이 늘면 이 파생 로직을 명시적으로 다시 봐야 한다

#### ONGOING은 이번 범위에서 제외

- **문제**: `status=UPCOMING`만 쓰면 오늘 진행 중인 축제가 "다가오는 순"에서 빠진다. 홈의 `GET /festivals/upcoming`은 "종료되지 않은 것"이라 진행 중을 포함해, 기준이 서로 다르다
- **선택**: 이번 작업은 `status=UPCOMING`만. ONGOING 포함은 별건으로 분리
- **대안**: `status` 다중값이나 새 값(NOT_ENDED 등)을 백엔드에 요청 — 백엔드 계약 변경이 선행되어야 한다
- **트레이드오프**: "다가오는 순"에서 오늘 개최 중인 축제가 안 보인다. 대학 축제 특성상 개최일 하루~사흘이라 노출 손실은 작다

#### sort 값 개명은 범위 밖

- **문제**: `UPCOMING`이 `sort`와 `status` 두 곳에 산다. 계약을 처음 읽는 사람이 헷갈린다 (DEC-0115가 "재검토 조건 — 프론트가 status 필터를 붙이는 때"로 예고한 자리)
- **선택**: 개명은 이 PR에서 하지 않는다. `sort=UPCOMING`을 그대로 두고 `status`만 결합
- **대안**: `sort=UPCOMING` → `sort=START_DATE`로 개명 — 백엔드 계약이라 백엔드가 정하고 프론트가 짝으로 따라가야 한다. 프론트의 `FestivalSort` 타입·`SORT_OPTIONS`·`SortDropdown`이 URL에 쓰는 값·이미 공유된 링크가 전부 걸린다
- **트레이드오프**: 겹치는 이름이 당분간 남는다. 다만 이 작업이 "UPCOMING을 sort에서 뗄 수 있다"는 근거가 된다 (greedy-team/festa-frontend#59)
- ⭐ **볼트 승격 권장** — `/capture`로 `knowledge/decisions/` 등록 검토. DEC-0115의 "재검토 조건"에 프론트가 실제로 도달했고, sort 개명의 선결 근거가 이 PR로 성립한다

### 📌 참고사항

- MSW 목(`src/mocks/handlers/festivals.ts`)은 이미 `VALID_STATUS` 검증 + `festivalStatus()` 필터를 갖고 있어 수정하지 않았다
- 백엔드의 `status` 파라미터는 `festa-backend#82`(PR #93)로 이미 머지·배포됐고, DEC-0115로 계약이 확정돼 있다. 이 작업은 그 위에서 프론트만 붙인다
- `festa-backend#141`(sort=LATEST 기준을 발행 시각 → 개최일)은 이 작업과 독립이다. 머지되면 이력 화면의 "최신순"이 이름대로 동작하게 되지만 프론트가 맞출 것은 없다
