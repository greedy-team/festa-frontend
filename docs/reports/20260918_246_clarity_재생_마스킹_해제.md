### 📌 작업 개요

Clarity 세션 재생에서 모든 텍스트가 `•`, 모든 이미지가 회색 상자로 치환돼 "무엇을 보다가 눌렀는가"를 알 수 없던 문제를 해소했다.
루트 레이아웃 `body`의 전체 마스킹 속성을 제거하고, 개인정보 처리방침의 Clarity 처리 항목 문구와 분석 동의 E2E 단언을 실제 동작에 맞췄다.
코드 밖 운영 작업(Clarity 대시보드 masking mode → Relaxed)이 함께 있어야 효과가 나는 변경이다.

### 🔍 문제 분석

운영 Clarity는 **수집 자체는 정상**이었다. 30일 기준 세션 12건, 동시 접속 2명, 20~25분 동안 14페이지를 도는 실제 탐색까지 잡혔다.
문제는 재생 화면이었다. 클릭 좌표·스크롤·마우스 궤적만 남아 "어느 위치를 눌렀는가"는 보이지만 "무엇을 보다가 눌렀는가"는 알 수 없었다.
이용 장면을 확인해 사용성을 개선하려고 도입한 도구가 목적을 달성하지 못하는 상태였다.

원인은 두 겹이다.

1. 루트 레이아웃 `body`에 걸린 전체 마스킹 속성 (코드)
2. Clarity 프로젝트의 masking mode = **Strict** (대시보드)

**둘 중 하나만 바꾸면 여전히 전부 가려진다.** 한쪽만 손대고 "안 된다"로 판단하기 쉬운 구조다.

### ✅ 구현 내용

#### 루트 레이아웃 body의 전체 마스킹 속성 제거

- **파일**: `src/app/layout.tsx`
- **변경 내용**: `<body>`에 붙어 있던 `data-clarity-mask` 속성 제거. `className`을 비롯한 나머지 속성과 주석은 그대로 둠
- **이유**: 이 속성 하나가 문서 전체를 마스킹 대상으로 만들고 있었음

#### 개인정보 처리방침의 Clarity 처리 항목 문구 수정

- **파일**: `src/app/privacy/page.tsx`
- **변경 내용**: 제2조 제2항 Clarity 행의 수집 항목을 실제 동작에 맞게 기술 — `쿠키 식별자, 화면 경로, 마우스·터치·스크롤 위치, 화면에 표시된 축제 정보를 포함한 화면 구조(입력창에 입력한 내용과 검색 화면은 제외)`
- **이유**: 마스킹 범위가 바뀌었으므로, 코드만 고치면 이용자에게 알린 내용과 실제 처리가 달라짐. 제3조 국외 이전 표는 이 항목을 참조하므로 한 곳만 고치면 양쪽이 맞음

#### 분석 동의 E2E의 마스킹 단언 전환

- **파일**: `e2e/analytics-consent.spec.ts`
- **변경 내용**: "본문 텍스트가 마스킹된다"에서 **"화면 내용은 담기고 입력값은 빠진다"** 로 전환. 본문에 `PRIVATE_TEXT_CANARY_233` 링크를 심고, 압축 해제한 실제 Clarity 페이로드에 그 문자열이 담기는지 확인. 검색 입력에 넣은 `PRIVATE_INPUT_CANARY_233`은 페이로드에 없어야 통과
- **이유**: 마스킹 해제가 실제로 먹혔는지를 검증하는 동시에, "전송이 아예 없어서 통과"하는 상황을 막는 가드 역할

#### 분석 연결 운영 문서에 근거 기록

- **파일**: `docs/analytics-setup.md`
- **변경 내용**: 관리 화면 확인 절에 Relaxed 근거, 속성 판정 방식, 강제 마스킹 범위, 검색어 보호 경계를 기록
- **이유**: 다음 사람이 대시보드 설정과 코드 중 어느 쪽을 봐야 하는지 문서 한 곳에서 알 수 있게 함

### 🧭 결정 기록 (ADR)

#### 마스킹 속성을 `false`로 두지 않고 제거

- **문제**: 마스킹을 끄려고 `data-clarity-mask="false"`로 바꾸면 여전히 전부 가려진다
- **선택**: 속성 자체를 제거
- **근거**: `microsoft/clarity`의 `packages/clarity-js/src/layout/dom.ts`가 `Constant.MaskData in attributes`로 **존재 여부만** 검사한다. 값은 보지 않는다 (2026-09-18 확인)
- **대안**: 값을 `"false"`로 두기 — 동작하지 않는다. 껐다고 착각한 채 대시보드만 의심하게 된다
- **트레이드오프**: 없음. 다만 "값이 아니라 존재로 판정된다"는 사실이 코드만 봐서는 드러나지 않아 문서에 남겼다

#### 마스킹 해제 범위를 코드가 아니라 녹화 대상 경계로 가른다

- **문제**: 마스킹을 풀면 검색어가 재생에 노출되는가
- **선택**: 마스킹은 풀되 녹화 대상 경계는 그대로 둔다. 검색어 보호는 `src/lib/analytics.ts`의 `analyticsRecordingAllowed`·`analyticsPage`가 담당하며, `/search`와 쿼리·해시가 있는 URL에서는 Clarity를 **아예 로드하지 않는다**
- **대안**: 검색 화면만 선택적으로 마스킹 — 마스킹은 "가린 채 업로드"가 아니라 "애초에 안 보냄"보다 약한 보호다. 경계로 막는 쪽이 더 강하고, 이미 그렇게 되어 있었다
- **트레이드오프**: 검색 화면의 이용 장면은 앞으로도 볼 수 없다. 의도된 선택이다
- ⭐ **볼트 승격 권장** — 개인정보 처리 범위와 직결되고 되돌리는 비용이 크다 (볼트에 `DEC-0211`로 등록됨, `DEC-0203`을 대체)

### 🔧 주요 변경사항 상세

#### 마스킹 해제가 걸리는 두 곳

| 층 | 무엇 | 이번 변경 |
| --- | --- | --- |
| 코드 | `body`의 `data-clarity-mask` | 제거함 |
| 대시보드 | Clarity 프로젝트 masking mode | Strict → Relaxed (운영 작업) |

**특이사항**:

- **입력창·드롭다운은 masking mode와 무관하게 Clarity가 강제로 마스킹한다.** 해제할 수 없다 — 그래서 E2E가 입력값 부재를 단언해도 항상 통과한다
- **이미 수집된 세션은 소급 복구되지 않는다.** 마스킹된 내용은 애초에 업로드되지 않았기 때문이다
- **masking mode 변경은 반영까지 최대 1시간이 걸리고, 새 녹화에만 적용된다**

#### 건드리지 않은 것

- `src/lib/analytics.ts` — 녹화 대상 경계. 검색어 보호의 실제 주체이므로 그대로 둠
- `src/components/analytics/Analytics.tsx` — Clarity 태그 로딩. 변경 없음

### 📌 참고사항

- **이 변경은 아직 배포되지 않았다.** 프로덕션 코드에는 여전히 마스킹 속성이 살아 있어, 대시보드만 Relaxed로 바꿔도 재생은 계속 가려진다. `develop` → `main` 배포 후 실제 재생 화면에서 내용이 보이는지 확인이 필요하다
- **E2E의 마스킹 단언이 코드가 아니라 대시보드 설정에 의존하게 됐다.** masking mode가 Relaxed가 아니면 실패한다. 이 테스트가 깨지면 코드보다 **Clarity 프로젝트 설정을 먼저** 확인한다
- 녹화 대상 화면은 전부 공개 축제 정보다. 개인정보를 표시하거나 입력받는 화면은 대상 목록에 없다
