# 축제 전체 페이지 검색 기능 연결

### 📌 작업 개요

축제 전체 페이지(`/festivals`) 상단의 검색창이 표시만 되고 동작하지 않던 문제를 수정했다.
장식용 `SearchPill`을 실제 GET 폼(`FestivalSearchForm`)으로 교체하고, 입력한 검색어(`q`)를
목록 API로 전달한다. 아티스트 전체 페이지(`/artists`)의 이름 검색과 같은 패턴이다.

### 🔍 문제 분석

- `/festivals` 페이지가 렌더하던 `SearchPill`은 `aria-hidden`에 `<input>`도 `<form>`도 없는
  표시 전용 컴포넌트다. 클릭·포커스·제출이 전부 불가능했다.
- 페이지가 `searchParams`에서 `q`를 읽지 않았고, `getFestivals`에도 `q` 파라미터가 없었다.
- 백엔드 `GET /festivals`는 이미 이름 검색어 `q`를 받는다(mock 핸들러도 `f.name.includes(q)`로
  처리). 프론트가 전달만 안 하고 있었다.
- 같은 유형의 버그가 아티스트 목록에서 한 번 있었다(ISS-0082 — "SearchPill이 표시 전용",
  "mock이 q를 지원하는데 프론트가 안 씀"). 그때 만든 `ArtistSearchForm`을 그대로 미러링했다.

### ✅ 구현 내용

#### 축제 목록 검색 폼 컴포넌트 추가

- **파일**: `src/features/festivals/components/FestivalSearchForm.tsx` (신규)
- **변경 내용**: `ArtistSearchForm`·`NavSearchForm`과 같은 GET 제출 폼. `type="search" name="q"`
  입력과 제출 버튼, `action="/festivals"`. `sort`(기본값 `LATEST`가 아닐 때)와 `artistId`를
  hidden input으로 실어 보낸다. `page`는 싣지 않아 검색 시 1페이지로 리셋된다.
- **이유**: JS 없이도 동작하는 서버 컴포넌트 폼이 이 화면의 다른 필터(`SortDropdown`)와 같은
  방식이다. 검색해도 걸어둔 정렬·필터가 풀리지 않게 한다.

#### 목록 API에 검색어 파라미터 추가

- **파일**: `src/features/festivals/api.ts`
- **변경 내용**: `getFestivals`의 `Params`에 `q?: string` 추가, `if (q) params.set("q", q)`.
- **이유**: 백엔드가 이미 받는 파라미터를 전달만 한다.

#### 페이지에서 검색어 처리

- **파일**: `src/app/festivals/page.tsx`
- **변경 내용**:
  - `searchParams` 타입에 `q?: string` 추가, `const q = params.q?.trim() || undefined`
  - `getFestivals` 두 호출(초기 + 페이지 상한 클램프 재요청)에 `q` 전달
  - `SearchPill` → `FestivalSearchForm`으로 교체 (import 정리)
  - 빈 상태 문구를 검색 여부로 분기: `q`가 있으면 `"{q}"에 해당하는 축제가 없습니다.`
  - placeholder: `학교 또는 축제 이름 검색` → `축제 이름 검색`
- **이유**: `q`가 목록에서 나온 필터 결과 0건과 데이터 자체가 0건을 구분해야 한다.
  placeholder는 학교 검색을 약속했지만 `q`는 축제명만 매칭하므로 문구를 실제 동작에 맞췄다.
  페이지네이션 `makeHref`는 이미 현재 쿼리 전체를 복사하므로(`q` 포함) 변경 없음.

#### E2E

- **파일**: `e2e/festivals-search.spec.ts` (신규)
- **변경 내용**: 목록 첫 축제 이름 일부를 검색어로 써서 "검색하면 결과가 그 이름으로 좁혀진다",
  "검색해도 `sort=UPCOMING`이 유지된다" 2건. `artists-search.spec.ts`와 같은 방식(검색어
  하드코딩 없이 구조만 검증 — DEC-0134).
- **파일**: `e2e/festivals-sort.spec.ts`
- **변경 내용**: "SearchPill은 아직 표시 전용" 오래된 주석을 정리(검색은 새 스펙이 따로 봄).

### 🧭 결정 기록 (ADR)

#### 공용 `SearchInput` 대신 전용 `FestivalSearchForm`을 만들었다

- **문제**: 실제 검색 입력이 필요한데, 공용 `SearchInput`(`"use client"`, 280px)과 공개 목록
  화면의 서버 컴포넌트 폼 패턴(`ArtistSearchForm`, 320px) 두 선택지가 있었다.
- **선택**: `ArtistSearchForm`을 미러링한 서버 컴포넌트 `FestivalSearchForm`.
- **대안**:
  - 공용 `SearchInput` 재사용 — `"use client"`라 현재 파라미터를 읽으려고 클라이언트 번들이
    붙고, 폭이 280px로 고정돼 시안(`search-pill` 320×36)·자매 화면(`/artists` 320px)과 어긋난다.
  - `ArtistSearchForm`을 제네릭으로 통합 — 요청 범위 밖의 리팩터링.
- **트레이드오프**: 폼 마크업 ~10줄이 `ArtistSearchForm`과 중복된다. 이 저장소가 아티스트
  목록에서 이미 택한 패턴이라 일관성을 우선했다.

#### q 길이 상한(50자) 초과 400은 일반 에러 화면으로 둔다

- **문제**: DEC-0160이 `q`를 trim 후 50자 상한으로 정하고 초과 시 백엔드가
  `FESTIVAL_INVALID_QUERY` 400을 낸다.
- **선택**: 별도 특수 처리 없이 기존 `fetchJson` 실패 경로("축제 목록을 불러오지 못했습니다")로
  떨어뜨린다.
- **대안**: 프론트에서 50자 사전 컷 또는 전용 안내 문구.
- **트레이드오프**: 아티스트 목록도 자신의 q 400을 특수 처리하지 않는다 — 선례와 동일하게 뒀다.
  전용 처리가 필요해지면 두 화면을 함께 다룬다.
