### 📌 작업 개요
관리자 로그인과 축제 검수 화면을 로컬 픽스처·MSW 목킹에서 실 백엔드(`http://161.33.7.55:8080`)로 전환. `adminFetch` 공통 계층을 신설해 인증 헤더·에러 계약을 한곳으로 모으고, 실 `api-docs.json` 대조에서 드러난 `/api` 경로 접두사와 발행 API 모양 차이를 반영했다.

### 🔍 문제 분석

기존 관리자 화면(`abd2062` 등)은 픽스처 데이터와 MSW 핸들러 위에서 조립돼 있었다. 실 API로 옮기며 세 가지가 걸렸다.

1. **경로 접두사 결정이 두 번 뒤집혔다.** `DEC-0084`("경로에 `/api`를 붙이지 않는다")는 이전 백엔드 PR #28을 근거로 세운 결정이었는데, 이번 착수 전 재대조에서 백엔드 PR #62가 모든 경로에 `/api` 접두사를 다시 추가한 것을 `api-docs.json`으로 확인했다. `DEC-0084`를 폐기하지 않고 그대로 두면 `LOGIN_PATH`·`adminFetch` 예정 경로·MSW 핸들러가 전부 404를 낸다.
2. **인증 헤더·401 처리·에러 응답 파싱이 로그인(`auth/api.ts`)과 축제 조회(`festival/api.ts`) 양쪽에 각각 흩어져 있었다.** 실 API로 옮기면 두 곳 모두 토큰 첨부, `TOKEN_EXPIRED`/`UNAUTHORIZED` 처리, 에러 바디 파싱이 필요해지는데 따로 구현하면 계약이 갈릴 여지가 크다.
3. **축제 검수 화면의 일괄 발행 UI가 실 API 모양과 맞지 않았다.** 픽스처 기반 설계는 다중 선택 체크박스로 여러 축제를 한 번에 발행하고 부분 성공/실패 배너를 보여주는 구조였는데, 실 API(`api-docs.json`의 `FestivalPublishResponse`)는 축제 1건당 발행/해제 엔드포인트만 제공한다. 서버에 없는 일괄 처리 API를 프론트에서 흉내 내려면 N번 호출을 조합하고 부분 실패를 프론트가 직접 집계해야 해서, 존재하지 않는 서버 계약 위에 클라이언트 상태 기계를 얹는 셈이 된다.

### ✅ 구현 내용

#### `adminFetch` 공통 계층 신설
- **파일**: `src/lib/adminFetch.ts` (신규), `src/app/admin/providers.tsx`, `src/lib/adminError.ts`
- **변경 내용**: `adminFetch<T>(path, init?)`가 `/api` 접두사 부착, `Authorization` 헤더 첨부, 실패 시 응답 바디를 파싱해 `AdminApiError(errorCode, status)`를 던지는 것까지 전담한다. `AdminProviders`에 401(`TOKEN_EXPIRED`·`UNAUTHORIZED`) 발생 시 로그인 화면으로 리다이렉트하는 공통 처리를 추가했다. `adminError.ts`에 `INVALID_PAGE`·`INVALID_PAGE_SIZE` 에러 문구를 보강했다.
- **이유**: 로그인과 축제 조회가 각자 헤더·에러 파싱을 구현하면 한쪽만 고치고 다른 쪽을 놓치는 사고가 나기 쉽다. 인증이 필요한 모든 호출이 이 함수 하나를 거치게 해서, 이후 화면이 늘어나도 인증·에러 처리를 다시 만들지 않게 했다.
- **`login()`을 `adminFetch` 위로 재작성** — `src/features/admin/auth/api.ts`. 기존에 직접 `fetch`를 호출하며 헤더·에러 처리를 자체 구현하던 코드를 걷어내고 `adminFetch` 호출 하나로 줄였다.

#### `/api` 경로 접두사 정정 (`DEC-0084` 폐기)
- **파일**: `src/lib/adminFetch.ts`, `src/features/admin/auth/api.ts`, `src/mocks/handlers/adminAuth.ts`
- **변경 내용**: `adminFetch`가 모든 경로 앞에 `/api`를 붙이도록 하고, MSW 로그인 핸들러 경로도 `/api/admin/auth/login`으로 맞췄다.
- **이유**: 착수 전 재대조가 없었다면 `DEC-0084`를 그대로 따라 무접두사 경로로 구현했을 것이고, 실 서버에 붙이는 순간 전부 404가 났을 것이다. 결정이 근거로 삼은 백엔드 PR #28이 이후 PR #62로 재차 뒤집혔다는 사실을 `api-docs.json` 대조로 확인한 뒤에만 반영했다 — 재대조 없이 기존 문서만 믿고 진행했다면 놓쳤을 지점이다.

#### 일괄 발행 → 건별 발행/해제 전환
- **파일**: `src/features/admin/festival/api.ts`, `src/features/admin/festival/components/FestivalReviewScreen.tsx`, `src/features/admin/festival/components/FestivalReviewTable.tsx`, `src/features/admin/festival/types.ts`, `src/features/admin/festival/queries.ts`, `src/lib/adminEnums.ts`
- **변경 내용**: `AdminFestival` 타입을 실 스키마(`FestivalReviewItem`)에 맞춰 `publishedAt`·`blockers: PublishBlockerReason[]`로 재정의했다. 프론트에서 발행 가능 여부를 추정하던 `publishBlocker()` 계산 로직을 삭제하고, 서버가 내려주는 `blockers[]`(라인업 없음 등 3종)를 그대로 표시한다. 체크박스 다중 선택·부분 성공 배너 등 일괄 발행 UI 전체를 걷어내고 행 단위 발행/해제 버튼으로 바꿨다. 전용 API가 없는 필터 칩 건수도 함께 제거했다.
- **이유**: 서버에 없는 일괄 처리를 프론트가 흉내 내면 N번 호출 조합과 부분 실패 집계라는, 서버 계약에 없는 상태를 클라이언트가 새로 만들어야 한다. 서버가 이미 발행 가능 여부를 `blockers[]`로 계산해 내려주므로 프론트가 같은 판단을 다시 하는 것도 계산이 어긋날 여지만 늘린다. 건별 처리로 좁히면 화면 로직이 서버 응답을 그대로 반영하는 것으로 끝난다.

#### 죽은 코드 정리
- **파일**: `src/features/admin/festival/fixtures.ts` (삭제), 그 외 위 변경에 딸린 미사용 타입·훅
- **변경 내용**: 픽스처 파일 삭제, `publishBlocker`·`getFestivalCounts`·`usePublishFestivals`·`BulkPublishResult`·`PublishFailure` 등 일괄 발행 관련 타입·함수·훅을 전부 제거했다.
- **이유**: 실 API 연동 후에도 픽스처와 미사용 일괄 처리 코드가 남아 있으면 다음 작업자가 어느 쪽이 실제 경로인지 헷갈린다.

### 🔧 주요 변경사항 상세

#### src/lib/adminFetch.ts (신규)
`adminFetch<T>(path, init?)`가 `/api` 접두사 부착, 토큰 첨부, 실패 응답 파싱 후 `AdminApiError` throw까지 담당한다. 이후 인증이 필요한 모든 관리자 API 호출(`auth/api.ts`, `festival/api.ts`)이 이 함수 위에서 동작한다.

#### src/features/admin/festival/types.ts
`AdminFestival.blockers`가 `PublishBlockerReason[]` 타입으로 서버 응답을 그대로 옮긴다. `FestivalReviewTable`은 `festival.blockers.includes(PUBLISH_BLOCKER.LINEUP_EMPTY)` 같은 형태로 이 배열을 직접 참조해 발행 가능 여부를 판단한다 — 프론트가 별도로 재계산하지 않는다.

**특이사항**:
- MSW 로그인 핸들러(`mocks/handlers/adminAuth.ts`)는 삭제하지 않고 경로만 `/api` 접두사로 맞춰 남겼다. `NEXT_PUBLIC_API_MOCKING`이 꺼진 상태에서는 등록되지 않는 코드라 해가 없고, 오프라인 로컬 개발이 다시 필요해지면 그대로 쓸 수 있다.

### ⚠️ 남은 한계

이번 태스크에서 실행하지 못한 검증 두 가지는 코드로 해결할 수 없는 외부 의존성이라 미루는 것으로 문서화한다.

- **브라우저 종단 검증(로그인 → 목록 조회 → 발행/해제)은 백엔드 CORS 허용 PR #61이 머지된 뒤 별도로 실행한다.** 로컬 `pnpm dev`에서 실서버(`161.33.7.55:8080`)로 요청하면 브라우저가 CORS로 막는다 — `curl -i`로 응답 헤더를 직접 확인한 결과 `Access-Control-Allow-Origin`이 없다. curl은 CORS 프리플라이트를 거치지 않으므로 API 자체는 curl로 확인할 수 있지만, 브라우저 fetch는 이 헤더가 없으면 성공 응답도 프론트 코드에 전달되지 않는다. PR #61 머지 전까지는 브라우저에서 로그인·목록·발행·해제 흐름을 실제로 눌러볼 방법이 없다.
- **실 계정으로 로그인 curl 확인은 하지 않았다.** `AdminAccountSeeder`가 심는 실 자격 증명을 이 작업에서 알 수 없다. 잘못된 자격 증명으로는 에러 응답 모양(`AdminApiError` 계약과의 일치)만 확인할 수 있고, 성공 응답(`accessToken` 발급 및 그 모양)까지는 이번 범위에서 확인하지 못했다.

두 항목 모두 코드를 우회해 확인하려 하지 않았다 — PR #61 머지, 실 계정 확보라는 외부 조건이 풀린 뒤 별도로 재검증해야 한다.

### 📌 참고사항
- 관리자 화면(A0~A5)은 `DESIGN.md`의 적용 범위 밖이라 이번 작업에서 토큰 준수 여부를 검토하지 않았다.
- `docs/api-docs.json`은 이번 재대조에 쓴 실 스펙 파일로, 저장소에 아직 커밋되지 않은 채 남아 있다(작업 트리에 untracked 상태) — 이번 태스크의 변경 범위가 아니라 그대로 두었다.
