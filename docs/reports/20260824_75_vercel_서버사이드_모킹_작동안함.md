### 📌 작업 개요
`NEXT_PUBLIC_API_MOCKING`을 켜도 Vercel에 배포된 서버 컴포넌트는 실제 백엔드로 요청을 보내다가 실패하는 문제 수정. 네트워크 레벨 인터셉션 대신 MSW 핸들러를 직접 호출하는 방식으로 바꾸고, 관련 값 표기를 `enabled`/`disabled`에서 `true`/`false`로 통일했다.

### 🔍 문제 분석
`src/instrumentation.ts`가 Node 런타임에서 `msw/node`의 `setupServer()`로 `fetch`를 가로채는 구조였다. 로컬 `pnpm dev`·`next start`에서는 정상 작동했지만, Vercel 서버리스 함수 환경에서는 이 인터셉션이 걸리지 않아 실제 API 도메인으로 요청이 나가 실패했다(Vercel Function 로그에서 `fetch failed`로 확인).

로컬에서 `NEXT_PUBLIC_API_MOCKING=true`로 `pnpm build && pnpm start`를 직접 띄워 검증한 결과 코드 로직 자체는 정상이었고, Vercel 서버리스 함수 환경에서만 인터셉션이 안 걸리는 것으로 원인을 좁혔다.

### ✅ 구현 내용

#### fetchJson이 네트워크 대신 MSW 핸들러를 직접 호출
- **파일**: `src/lib/api.ts`
- **변경 내용**: 모킹이 켜져 있으면 `fetchMockJson()`을 거친다. `src/mocks/handlers`를 동적 import한 뒤 `${API_BASE}${path}`로 `Request`를 만들어 handlers 배열을 순회하며, 매칭되는 핸들러의 `RequestHandler.run()`을 직접 호출해 응답을 받는다.
- **이유**: `run()`은 MSW가 공개한 API로, 네트워크 패치 없이 핸들러 로직만 실행해 `Response`를 돌려준다. 실행 환경(로컬/Vercel 서버리스)에 의존하지 않아 인터셉션 문제 자체를 우회한다.

#### 모킹 플래그 값을 true/false로 통일
- **파일**: `src/lib/mocking.ts`(신규), `src/lib/api.ts`, `src/app/layout.tsx`, `src/instrumentation.ts`
- **변경 내용**: `NEXT_PUBLIC_API_MOCKING === "true"` 비교를 `src/lib/mocking.ts`의 `MOCKING_ENABLED` 상수 하나로 모으고, 나머지 세 파일은 이 값을 import해서 쓴다.
- **이유**: 같은 문자열 비교가 세 파일에 흩어져 있으면 값 표기(`enabled`→`true`)를 바꿀 때마다 전부 손대야 한다. 값을 판정하는 곳을 한 곳으로 좁혔다.

#### 문서 갱신
- **파일**: `README.md`, `src/mocks/README.md`, `src/mocks/CODE_GUIDE.md`, `src/mocks/MOCKING_STRATEGY.md`, `src/mocks/MockProvider.tsx`, `src/mocks/handlers/adminAuth.ts`
- **변경 내용**: `enabled`/`disabled` 표기를 `true`/`false`로 맞추고, "모킹 플래그는 로컬 전용이라 Vercel에 등록하지 않는다"는 이제 틀린 서술을 "Vercel에도 등록해 배포 환경에서 동일하게 동작한다"로 수정.
- **이유**: 이번 수정으로 Vercel 배포에서도 모킹이 실제로 동작하게 됐으므로, 그 반대로 적힌 안내를 그대로 두면 오해를 만든다.

### 🧭 결정 기록 (ADR)

### Vercel에서 모킹 인터셉션 문제를 인터셉션 자체를 우회해서 해결

- **문제**: `msw/node`의 `setupServer()` 기반 fetch 인터셉션이 Vercel 서버리스 함수에서 걸리지 않았다. 원인이 Vercel 내부 실행 모델(요청마다 뜨는 함수 vs 상시 프로세스)에 있는 것으로 추정되나, Vercel·MSW·Turbopack 조합의 정확한 내부 동작은 문서화돼 있지 않다.
- **선택**: 인터셉션 방식을 고치려 하지 않고, `fetchJson`이 `RequestHandler.run()`으로 handlers를 직접 실행하도록 우회했다.
- **대안**:
  - Vercel 번들링 설정을 파고들어 인터셉션이 걸리도록 고치기 — 원인이 플랫폼 내부 블랙박스라 고칠 수 있다는 보장이 없고, 고친다 해도 Vercel 쪽 변경에 다시 깨질 위험이 있다.
  - 픽스처 데이터를 별도로 다시 읽어오는 함수 작성 — 이미 있는 handler 로직(페이지네이션, 에러 응답 등)을 중복 구현하게 된다.
- **트레이드오프**: 서버 사이드 모킹이 이제 `msw/node`의 네트워크 인터셉션에 의존하지 않으므로, `src/instrumentation.ts`의 `server.listen()`은 서버 컴포넌트 fetch 경로에서는 사실상 더 이상 필요 없다. 다만 이번 이슈 범위 밖이라 남겨뒀다 — 필요하면 후속 정리 대상이다.
- ⭐ **볼트 승격 권장** — MSW 서버 사이드 모킹이 Vercel 서버리스 환경에서 안 걸린다는 사실은 이 프로젝트에 국한되지 않는 재사용 가능한 교훈이다.

### 🧪 테스트 및 검증
- `pnpm exec tsc --noEmit` 통과
- `pnpm lint` 통과 (기존과 무관한 `public/mockServiceWorker.js` warning 1개만 남음)
- `NEXT_PUBLIC_API_MOCKING=true NEXT_PUBLIC_API_BASE_URL=https://api.every-festa.com pnpm build && pnpm start`로 로컬 프로덕션 서버를 띄워 홈(`/`)에 목데이터("라치오스 2026", "루카스 2026" 등)가 정상 렌더되는지 확인
- 빌드 로그에서 실제 API 호출 실패("실패 null") 로그가 사라진 것을 확인

### 📌 참고사항
- Vercel Production/Preview의 `NEXT_PUBLIC_API_MOCKING` 값도 이번 작업 중 `true`로 맞춰뒀다.
- `src/instrumentation.ts`는 남아있지만 서버 사이드 fetch 경로에서는 더 이상 실질적으로 쓰이지 않는다. 정리는 이번 이슈 범위 밖으로 남겨둔다.
