## 본문

## 📝 현재 문제점

축제 상세의 주최 이름을 눌러서 갈 곳이 없다. "이 학교가 그동안 어떤 축제를 열었고 누가 왔는지"가 이 서비스의 성격(과거 라인업 아카이브)에 직접 닿는 정보인데 화면이 없다.

`GET /hosts/{id}`는 MSW 목이 이미 응답한다. 배너·로고·약칭·지역, 다가오는 축제, 축제 이력, 자주 온 아티스트 3명까지 들어 있다.

DESIGN.md 컴포넌트 시트에는 `upcoming-host-card`(356×372)가 사용처를 이 화면으로 적어둔 채 만들어지지 않은 상태로 남아 있다.

## 🛠️ 해결 방안 / 제안 기능

`/hosts/[id]` 경로를 만들고 `GET /hosts/{id}` 응답으로 네 영역을 그린다 — 히어로, 다가오는 축제, 축제 이력, 자주 온 아티스트. 이 화면이 축제 상세와 아티스트 상세를 잇는 허브가 된다.

같은 이슈에서 이 화면의 구성 요소와 배치 원칙을 DESIGN.md에 추가한다. 1440 좌표 레이아웃은 옮기지 않는다 — 시안의 픽셀은 비율과 위계의 근거이지 계약이 아니고, 세부는 피그마를 직접 본다.

## ⚙️ 작업 내용

1. 라우트 — `/hosts/[id]`. 주최 단건 조회 함수를 추가한다

2. 히어로 — 배너, 로고, 이름, 약칭, 지역

3. 다가오는 축제 — `upcoming-host-card`를 만들고 `upcomingFestivals`를 그린다. 각 카드는 축제 상세로 링크한다

4. 축제 이력 — `festival-card` 그리드. 응답이 주는 2건과 전체 건수를 함께 표기한다

5. 자주 온 아티스트 — 순위, 이름, 출연 횟수. 각 항목은 아티스트 상세로 링크한다

6. 없는 주최 — 404를 받으면 Next.js의 not-found로 넘긴다

7. DESIGN.md에 이 화면의 구성 요소와 배치 원칙을 범용 규칙으로 추가한다. 좌표 레이아웃은 옮기지 않는다. 새로 만든 공용 컴포넌트는 `/showcase`에 등재한다

## 📌 확정한 설계 결정

- **`host.type`을 화면에 쓰지 않는다.** 목 응답에는 있지만 확정된 ERD에는 없는 필드다. 목 핸들러 주석도 스펙 원문 기준으로 넣어둔 것이며 팀 확인이 나면 지울 자리라고 적어 두었다. 주최 표기는 이름·약칭·지역으로 충분하다
- **자주 온 아티스트의 id는 이 응답의 `artistId`를 쓴다.** 축제 상세의 라인업은 같은 대상을 `id`로 준다. 이 갈림은 이슈 #40이 다루고, 결론이 나면 그때 맞춘다
- **축제 이력의 「더 보기」는 링크를 걸지 않고 자리만 둔다.** 응답이 이력 2건과 전체 건수만 주고, 전체 목록은 축제 목록 화면(`hostId` 필터)의 몫이다. 그 화면이 없는 동안은 Footer에서 쓴 방식대로 링크가 아닌 요소로 둔다 — 데모 중에 404가 나지 않게 한다
- **다가오는 축제가 0건인 상태를 정상으로 둔다.** 대학 축제는 봄·가을에 몰리므로 대부분의 시기에 이 영역이 빈다. 영역을 감출지 빈 상태 문구를 둘지는 구현에서 정하고 결과를 보고서에 남긴다
- **D-day는 서버가 준 값을 그대로 쓴다.** 이 응답의 `upcomingFestivals`에 `dday`가 들어 있다

## 🚫 범위에서 빼는 것

- **연도 필터.** 응답의 `availableYears`가 선택지를 주지만, 같은 응답이 이력을 2건만 주므로 필터가 걸 대상이 화면에 없다. 연도별 조회는 축제 목록 화면(`hostId` + `year`)의 몫이다
- 축제 이력 페이지네이션. 같은 이유다
- 축제 목록 화면. 별도 이슈다
- 주최 등록·수정. 관리자 화면 범위이고 디자인 시스템 적용 대상도 아니다
- 광고 슬롯. 홈 외 화면의 광고 정책이 없다
