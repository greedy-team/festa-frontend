## 📝 현재 구조의 문제

이슈 #34(디자인 시스템 구축)의 최종 브랜치 리뷰에서 Minor로 분류돼 머지를 막지 않고 넘어간 항목들이다. 하나씩은 작지만 이후 화면 작업이 전부 이 위에 올라가므로, 지금 정리하면 뒤에 오는 20여 개 컴포넌트가 같은 문제를 물려받지 않는다.

### 컴포넌트 규약이 제각각이다

태스크를 나눠 만든 흔적이 그대로 남았다.

- 스타일 축을 고르는 prop 이름이 다르다 — Button과 Chip은 `variant`, Badge는 `tone`, SearchPill은 `size`
- 내용을 받는 prop이 다르다 — `children` / `placeholder` / `label`
- 변형과 상태의 조합을 다르게 모델링했다 — Button은 별도 상수와 런타임 분기(`SHEET_SECONDARY`), Chip은 lookup 키(`filter-active`)
- lookup 객체 타입이 다르다 — `Record<K, string>` vs `as const`
- 네이티브 속성을 전개하는 것은 Button 하나뿐이다

### 동작상 걸리는 것

- `Chip`의 `active`가 `variant="sheet"`일 때 조용히 무시된다. `<Chip variant="sheet" active>`가 타입 검사를 통과하고도 비활성으로 렌더된다
- `Button`이 `variant` 3종 × `size` 3종으로 조합 9개를 허용하는데 DESIGN.md가 이름 붙인 것은 5종이다. 나머지 4개도 유효한 색×높이 조합이라 잘못된 화면을 만들지는 않지만, 타입만 보고는 어느 조합이 시안에 있는지 알 수 없다. 다만 5종을 유니온으로 못박으면 안 된다 — DESIGN.md 자체가 이미 6번째 조합을 쓴다(`button-primary`는 180×48인데 `search-filter-panel`의 「검색하기」는 같은 primary에 160×52다). 화면이 몇 개 나와 실제로 쓰이는 조합이 드러난 뒤에 화이트리스트를 만드는 것이 순서다
- `Button`에 `type="button"` 기본값이 없다. DESIGN.md의 `search-filter-panel`(초기화 + 검색하기)이 곧 나오는데, 폼 안에서 기본값 `submit`이 의도치 않은 제출을 일으킨다
- `aria-current="page"`가 한 곳도 없다. Header와 showcase 인덱스 둘 다 현재 위치를 색과 밑줄로만 전달해서 스크린리더에는 아무 표시가 없다
- `<body>`에 기본 글자색이 없다. 토큰 클래스를 달지 않은 텍스트는 ink가 아니라 브라우저 기본 검정을 상속한다. 지금은 모든 컴포넌트가 토큰을 달고 있어 드러나지 않는 잠재 문제다

### 토큰 리셋이 절반에서 멈췄다

`--color-*`와 `--radius-*`만 리셋했고 `--text-*`, `--font-weight-*`, `--leading-*`, `--tracking-*`, `--shadow-*`는 Tailwind 기본값이 남아 있다. 그래서 `text-lg`, `font-light`, `leading-relaxed`, `tracking-wide`, `shadow-xl`이 전부 살아 있고, 각각 DESIGN.md의 Don'ts(line-height 1.21 고정 / 무게 300·800 없음 / letter-spacing 조정 금지 / 그림자 2개뿐)를 정면으로 뚫는다.

이슈 #34의 스펙이 색과 radius만 약속했으므로 위반은 아니지만, "문서 규칙을 기계 제약으로 바꾼다"는 논거가 절반에서 멈춘 상태다.

### 중복과 매직넘버

- `showcase/layout.tsx`가 Chip의 클래스 문자열을 그대로 복제했다. Chip이 `<span>`이고 네이티브 속성을 통과시키지 않아 `<Link>` 자리에 쓸 수 없었기 때문이다. 이슈 #34가 막겠다던 "같은 요소가 여러 벌 생긴다"가 브랜치 안에서 이미 한 번 일어났다
- `Header.tsx`의 `ml-[75px]`은 Pretendard 26/700으로 렌더된 FESTA 로고의 실측 폭에 묶인 매직넘버다. 로고 크기가 바뀌면 메뉴 위치가 어긋나는데 근거가 코드에도 스펙에도 없다
- InlineFilter와 Chip도 SearchPill과 같은 부류다 — 조작할 수 없는데 시각적으로는 컨트롤로 보인다. 현재는 showcase에만 있어 비용이 유예됐을 뿐, 실제 화면에 들어가면 SearchPill과 같은 처리가 필요하다

### 규칙이 추적되지 않는 파일에만 있다

이슈 #34 스펙의 "className은 기본 클래스와 충돌하지 않는 속성만 받는다"는 규칙이 gitignore 대상인 스펙 문서에만 있다. 인라인 주석도 Button 하나에만 붙어 있다. 표기 규칙 3건을 `.claude/rules/coding-principles.md`로 옮긴 것과 같은 이유가 이 규칙에도 적용된다.

## 🛠️ 개선 방향

우선순위 순으로 묶었다. 전부를 한 번에 할 필요는 없다.

1. 동작에 걸리는 것부터 — Button의 `type="button"` 기본값, Chip의 `active` 무시 문제
2. 접근성 — `aria-current="page"`, body 기본 글자색, InlineFilter/Chip의 노출 방식
3. 컴포넌트 규약 통일 — prop 이름과 변형 모델링을 한 벌로 맞춘다. 나머지 21종을 만들기 전에 하는 것이 싸다
4. 토큰 리셋 범위 확장 여부 판단 — 남은 네임스페이스도 리셋할지, 색·radius에서 멈출지 결정한다
5. className 규칙을 `.claude/rules/coding-principles.md`로 이관
6. `showcase/layout.tsx`의 Chip 복제 — 3번을 하면 함께 풀린다
7. `Header.tsx`의 `ml-[75px]` 근거를 코드나 스펙에 남기거나, 레이아웃을 폭에 의존하지 않게 바꾼다
