## 본문

## 🔍 현재 문제점

- Lighthouse 성능 기준선과 개선 전후 스크린샷이 없어 데모데이에서 개선 효과를 설명할 근거가 부족합니다.
- 유입·축제 탐색 경로와 사용자가 겪는 불편을 관찰할 분석 체계가 준비되지 않았습니다.
- 개선 대상의 선정 이유와 목표 지표의 근거를 포함한 성능·사용 경험 보고서가 필요합니다.

## 💡 해결 방안 / 제안 기능

- Lighthouse로 수정 전 상태를 먼저 보존하고, 분석 도구 도입 후와 필요한 최적화 후를 동일 조건으로 비교합니다.
- GA4로 유입·탐색을 분석하고 Clarity로 히트맵·이용 장면을 확인합니다. Clarity는 사용 조건 확인 후 도입합니다.
- 확인된 병목과 반복되는 사용자 불편을 우선 개선하며, 목표를 이미 충족한 영역은 불필요하게 변경하지 않습니다.
- 공개 서비스 화면을 분석 대상으로 하고 민감정보·관리자 이용·팀 테스트는 제외합니다.

## 🔧 작업 내용

- [ ] 데모 일정·분석 담당자·배포 및 수집 범위를 확정한다.
- [ ] 홈·축제 목록·축제 상세·검색의 수정 전 Lighthouse 결과와 화면을 확보한다. 홈의 축제 유무를 구분한다.
- [ ] 모바일·데스크톱 각각 동일 조건에서 5회 측정하고 원본 보고서·중앙값·범위를 보존한다.
- [ ] GA4와 Clarity를 도입하고 동의·거부·철회, 마스킹, 제외 화면의 미수집을 확인한다.
- [ ] 페이지 조회·콘텐츠 선택·검색 결과·공식 링크 선택을 확인하고 중복 집계와 민감정보 전송이 없는지 검증한다.
- [ ] 분석 도구만 추가한 상태의 Lighthouse 결과를 확보해 계측 비용을 분리한다.
- [ ] 측정 근거로 성능 개선 대상을 정하고 각 대상의 선정 이유·목표·목표 선정 근거를 기록한다.
- [ ] 모바일 잠정 목표 Performance 90점 이상, LCP 2.5초 이하, CLS 0.1 이하, TBT 200ms 이하를 검증한다. 변경이 필요하면 작업 전에 사유를 기록한다.
- [ ] 사용자 행동 기준선을 수집하고 반복 불편 1~2개를 선정해 개선한다. 표본 부족 시 사용성 테스트를 별도로 기록한다.
- [ ] 수정 전·계측 추가 후·최적화 후 Lighthouse 스크린샷 및 수치, UX 관찰·개선 결과를 데모 리포트로 정리한다.
- [ ] 실제 미측정·미완료 항목과 실사용 데이터의 한계를 명시한다. 계측 설치만으로 전체 작업을 완료 처리하지 않는다.
