## 본문

## 📝 현재 문제점

화면 작업을 시작할 기반이 없다.

- `.claude/rules/DESIGN.md`는 1001줄로 정리돼 있는데 실제 전역 스타일은 Next.js 초기 생성값 그대로다
- 공용 컴포넌트가 하나도 없다
- 모든 페이지를 감싸는 헤더와 푸터가 없어, 화면을 만들어도 서비스 형태로 보이지 않고 화면 사이 이동을 확인할 수 없다
- 글꼴이 Geist다. DESIGN.md는 Pretendard이고, 문서 스스로 "구현 시 Pretendard 로드 필요"라고 적어 두었다

이 상태에서 화면 이슈부터 진행하면 사람마다 색과 간격을 직접 적고 버튼을 각자 만들게 된다. 같은 요소가 여러 벌 생기고, 크기와 색이 조금씩 다른 채로 굳는다. 나중에 시안이 바뀌면 고칠 자리를 전부 찾아다녀야 한다.

## 🛠️ 해결 방안 / 제안 기능

DESIGN.md를 코드로 옮겨 화면 작업의 기반을 만든다. 토큰, 폰트, 아이콘, 공용 컴포넌트, 레이아웃 셸, 그리고 이것들을 눈으로 확인할 전시 화면까지 하나로 처리한다.

나누지 않는 이유는 서로 떨어지지 않기 때문이다. 같은 파일을 건드리고, 토큰이 있어야 컴포넌트를 만들 수 있어 병렬로 진행할 수도 없다. 패키지만 바뀐 PR은 리뷰할 내용도 없다.

## ⚙️ 작업 내용

1. 패키지 추가 — lucide-react, pretendard. 도입 기준은 `docs/packages.md`를 따른다

2. 디자인 토큰 — DESIGN.md의 Colors, Typography, Layout, Elevation, Shapes를 전역 스타일로 옮긴다. 색 34, 타이포 26, radius 12, 그림자 2. spacing은 DESIGN.md의 10종(4·8·12·16·20·24·32·40·64·80)이 Tailwind 기본 4px 스케일과 정확히 일치해 별도 토큰을 두지 않는다

3. 폰트 — Geist를 제거하고 Pretendard로 교체한다. 한글 dynamic-subset을 셀프호스팅해 브라우저가 실제로 쓰는 글자만 내려받게 한다

4. 공용 컴포넌트 — DESIGN.md 명세 13종을 파일 5개로 만든다. Button, Badge, Chip, SearchPill, InlineFilter. 버튼 5종은 색 3가지 × 높이 3가지의 조합이고, 뱃지 4종은 색만 다르다. 폭은 컴포넌트 속성이 아니라 사용처가 정한다

5. 레이아웃 셸 — Container, Header, Footer를 만들고 RootLayout에 적용한다

6. 전시 화면 — `/showcase` 경로에 토큰과 모든 컴포넌트 변형을 늘어놓는다. 리뷰어가 이 경로 하나만 열면 시안과 눈으로 대조할 수 있다

## 📌 확정한 설계 결정

- shadcn/ui를 지금 도입하지 않는다. 이번 13종 중 Radix가 필요한 것이 없고, init이 심는 자체 토큰이 DESIGN.md 토큰 레이어와 이중화된다. 바텀시트나 드롭다운이 나올 때 도입한다
- 컨테이너는 유동으로 두고 태블릿 이하는 대응하지 않는다. DESIGN.md의 Laptop 행이 이미 "마진 축소, 컨테이너 가변"이라 지어내는 것이 아니고, 태블릿 이하는 문서가 미설계로 남겨 둔 영역이다
- 셸의 MVP 미존재 요소는 시안대로 그리되 링크로 만들지 않는다. 헤더의 벨·북마크·프로필과 푸터 링크 7개가 해당한다. 셋 다 로그인을 전제하고 나머지는 MVP에 화면이 없다. span으로 두면 시각적 완성도를 지키면서 데모 중 404가 나지 않는다
- 아이콘은 lucide-react. DESIGN.md가 "아이콘 시스템이 없다"고 직접 적어 둔 자리이고, 남은 화면까지 보면 15~20개가 필요하다

표기 규칙 3건은 `.claude/rules/coding-principles.md`의 「코드 규약」 절에 추가했다 — 치수는 리터럴로 색과 타이포는 토큰으로, 조건부 렌더는 삼중연산자로, CSS Module을 기본으로 쓰지 않기.

## 🚫 범위에서 빼는 것

DESIGN.md에 정의된 컴포넌트는 34개지만 이 이슈는 13개만 다룬다. 카드, 목록 행, 패널, 바텀시트는 특정 화면에서만 쓰이므로 해당 화면 작업에서 만든다. `docs/folder-structure.md`의 배치 기준이 "한 도메인에서 사용하면 해당 feature 폴더"로 정하고 있고, "빈 폴더나 빈 파일을 미리 만들지 않는다"는 원칙도 같은 문서에 있다.

히어로 4분할 캐러셀도 뺀다. 클릭 인터랙션이 미결이라 아직 만들 수 없다.

테스트 도구 선정도 별도 이슈로 둔다. Button과 Badge에는 로직이 없어, 클래스가 붙었는지 검사하는 단위 테스트는 동작이 아니라 구현 세부를 검사한다. 리팩터링할 때마다 깨지면서 아무 버그도 잡지 못한다. 이번 작업의 검증은 `/showcase` 화면이 맡는다.
