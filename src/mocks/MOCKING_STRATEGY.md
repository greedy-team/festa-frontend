# 프론트 API 모킹 방법 수립

**상태:** Implemented (아래 "5. 갱신" 참고 — 최초 작성 이후 구조가 일부 늘었다)
**작성:** 모킹 코드 담당

---

## 1. 문제 정의 (Context)

FESTA 프론트는 2인 체제로 진행 중이고, 화면 개발은 API 명세서를 기반으로 **모킹 데이터로 먼저** 진행하기로 했다(백엔드 완성을 기다리지 않고 프론트를 먼저 만들기 위함). 이 상황에서 다음 조건들이 결정에 걸린다.

- 팀원 한 명은 디자인·화면 코딩, 나머지 한 명(본인)은 모킹 코드를 전담한다. 즉 **화면을 만드는 사람과 모킹 데이터를 만드는 사람이 분리**되어 있다.
- 나중에 실제 백엔드가 붙을 때, **화면 코드를 다시 고치는 비용이 최소화**되어야 한다. 모킹은 "임시로 대충 만들고 버리는 것"이 아니라 실제 API 계약을 미리 검증하는 수단이어야 한다.
- API 명세서 자체가 여러 버전(초기 통합본 → 최종 통합본 → 개별 페이지 export → 에러 코드 마스터)으로 나뉘어 있고, **문서 간 필드명·범위·에러코드가 서로 다른 경우가 실제로 다수 발견됐다.** 모킹 데이터가 "어느 문서를 기준으로 만들어졌는지"가 불명확하면, 나중에 실제 API가 붙었을 때 "왜 프론트가 이렇게 짜여있지?"를 아무도 설명 못 하는 상황이 생긴다.
- 프론트 테스트 전략 문서(ADR)가 이미 "async Server Component는 E2E로만 검증 가능하다"고 결론 낸 상태다. 즉 **모킹이 단순히 화면을 눈으로 보기 위한 용도를 넘어서, Playwright E2E가 실제로 돌아가기 위한 전제 조건**이기도 하다.

## 2. 결정 (Decision)

### 2.1 도구: MSW(Mock Service Worker)를 쓴다

컴포넌트가 실제 `fetch()`를 그대로 호출하고, 그 요청을 네트워크 레벨에서 가로채는 방식을 택했다. 대안으로 "컴포넌트에 목업 데이터를 직접 props로 꽂아넣기"나 "별도 목업 서버(json-server 등)를 띄우기"도 있었지만:

- **컴포넌트 코드가 "지금 모킹 중인지 실제 API인지"를 몰라도 된다.** 나중에 실제 백엔드로 전환할 때 `NEXT_PUBLIC_API_MOCKING=false`와 `NEXT_PUBLIC_API_BASE_URL`만 바꾸면 되고, 화면 코드는 한 줄도 안 바꿔도 된다. 이게 "화면 담당"과 "모킹 담당"이 분리된 이번 체제에서 특히 중요하다 — 팀원이 API 응답 모양만 믿고 화면을 짜면 되기 때문이다.
- Next.js App Router가 async Server Component 위주라 서버(Node)와 브라우저 양쪽에서 fetch가 발생하는데, MSW는 두 환경을 모두 지원한다(`msw/node`, `msw/browser`). 별도 목업 서버 방식은 Server Component의 서버사이드 fetch까지 자연스럽게 커버하기 어렵다.
- 테스트 전략 문서가 이미 Playwright E2E를 채택한 상태인데, MSW로 만든 모킹은 **개발용 브라우저 실행과 E2E 테스트 실행에 동일한 handler를 재사용**할 수 있다. 목업 서버를 따로 띄우는 방식은 테스트 환경에서 서버 기동/포트 관리 같은 부가 비용이 생긴다.

### 2.2 데이터: 단일 소스(`db.ts`) + ID 참조 구조

각 handler가 자기 응답에 필요한 데이터를 개별적으로 하드코딩하지 않고, `fixtures/db.ts` 하나에 원본 데이터를 두고 모든 handler가 여기서 파생시킨다. 축제의 라인업도 아티스트를 이름이 아니라 `artistId`로 참조한다(관계형 DB의 외래키와 동일한 개념).

이유:
- 데이터가 여러 파일에 중복되면, 하나만 고치고 나머지를 놓치는 실수가 실제로 나기 쉽다 (예: "아이유"라는 이름이 festivals/artists/search 세 군데에 따로 있으면).
- 더 결정적인 이유는 **F-13 순환탐색(축제→아티스트→축제) E2E가 실제로 의미 있으려면, 라인업의 artistId가 진짜 존재하는 아티스트를 가리켜야 한다는 것**이다. 데이터를 흩어놓으면 이 정합성을 사람이 수작업으로 관리해야 하는데, ID 참조 구조로 만들면 애초에 깨질 수 없는 구조가 된다. 즉 이건 편의가 아니라 **테스트가 실제로 신뢰할 수 있는 결과를 내기 위한 전제 조건**이다.

### 2.3 도메인별 handler 분리, 공통 로직은 헬퍼로 추출

`festivals.ts`/`artists.ts`/`hosts.ts`/`search.ts`로 나누고, 페이지네이션·에러 응답은 `pagination.ts`/`errors.ts`로 공통화했다. (이후 `date.ts`/`appearances.ts` 두 헬퍼가 추가됐다 — "5. 갱신" 참고.)

- 도메인별 분리는 **API 명세서 자체의 섹션 구조(3. festivals, 4. artists...)를 그대로 따른 것**이다. 명세서 어디를 보고 있는지와 코드 어느 파일을 보고 있는지가 항상 1:1로 대응되게 해서, 스펙이 바뀌었을 때 어느 파일을 고쳐야 하는지 헷갈리지 않게 했다.
- 공통 헬퍼로 뺀 건 "한 곳만 고치면 전체에 반영되게" 하기 위해서다. 실제로 이번 작업 중 에러 응답 필드명이 `code`→`errorCode`로 확정됐을 때, `errors.ts` 한 줄만 고쳐서 10개 엔드포인트 전체에 즉시 반영됐다 — 만약 각 handler에 에러 응답을 하드코딩했다면 10번 따로 고쳐야 했을 것이다.

### 2.4 범위: 스펙이 명확한 도메인부터, 불명확한 건 후순위

10개 엔드포인트(festivals/artists/hosts/search)를 먼저 구현하고, lost-items(퀴즈 인증 흐름이 있어 상태 관리가 복잡하고 P1로 결정됨)와 admin(프론트 스코프 자체가 다름)은 제외했다.

우선순위 기준은 두 가지였다:
1. **테스트 전략 문서의 E2E 대상(F-13 순환탐색)에 필요한 도메인인가** — festivals/artists/hosts가 여기 해당한다.
2. **명세가 실제로 확정돼 있는가** — lost-items의 본인확인 퀴즈 API 2개는 작업 초반엔 문서에 아예 없었다가 나중에 확정됐는데, 그 사이 기간에 임의로 추측해서 모킹을 만들었다면 나중에 스펙 확정 시 다시 짜야 했을 것이다. 확정 안 된 스펙을 기반으로 먼저 만드는 건 총비용을 늘린다는 걸 이번 과정에서 실제로 확인했다(테스트 전략 문서도 같은 논리로 "명세 확정 전 목업 기반 E2E 미리 작성 안 함"을 원칙으로 삼고 있다).

### 2.5 문서 간 불일치 처리 방침: 주제별로 "가장 신뢰할 문서"를 따로 정하기

작업 도중 같은 스펙이 문서마다(심지어 한 문서 안에서도) 다르게 적힌 경우가 여러 번 나왔다(에러 필드명, 에러코드 철자, limit 유효범위 등). 이걸 그때그때 임의로 고르지 않고, **주제별로 기준 문서를 나눠서 정했다**:

- **에러 코드 이름/철자** → 에러 코드 마스터 문서(v1)를 기준으로 한다. 도메인별 에러코드를 전담해서 정리한 문서라 이쪽이 더 신뢰할 만하다고 판단했다.
- **그 외(필드 구조, 파라미터 정의 등)** → 검토 태그(검토-명준/검토-하은)가 붙은 개별 페이지 export를 기준으로 한다.

같은 기준 문서 안에서도 자체 모순이 있는 경우(예: `FESTIVAL_INVALID_LIMIT` 범위)는 임의로 정하지 않고 팀 확인 대기 상태로 코드에 주석으로 남겨뒀다.

## 3. 대안 검토 (Alternatives)

**대안 A: 화면 컴포넌트에 더미 데이터를 직접 하드코딩**
가장 빠르게 시작할 수 있지만, 나중에 실제 API 연동 시 컴포넌트 코드를 전부 다시 고쳐야 한다. "모킹 담당"과 "화면 담당"이 분리된 이번 체제와도 안 맞는다 — 화면 담당자가 API 응답 모양이 아니라 서로 다른 더미값을 각자 만들게 될 위험이 있다.

**대안 B: 별도 목업 서버(json-server 등) 구동**
정적 JSON 파일 기반이라 페이지네이션·에러 분기·검색 타입 분기 같은 동적 로직 구현이 번거롭고, Server Component의 서버사이드 fetch·테스트(E2E) 환경과의 통합이 MSW보다 부가 설정이 많다.

**대안 C: 명세 확정 전에도 추측해서 미리 다 구현**
분실물 퀴즈 API가 그 사례였다 — 실제로 스펙이 나중에 바뀌면서 추측했던 URL·필드명을 갈아엎어야 했다(2.4 참고). 이번 프로젝트에서 총비용이 더 크다는 게 확인돼 기각.

## 4. 결과 및 영향 (Consequences)

**장점**
- 화면 코드가 모킹/실제 API 전환 시 수정 없이 그대로 동작한다.
- 데이터 정합성이 구조적으로 보장돼(ID 참조), F-13 E2E가 신뢰할 수 있는 결과를 낸다.
- 스펙·에러코드가 바뀌어도 공통 헬퍼 몇 줄만 고치면 전체에 반영된다.
- 여러 문서 간 불일치를 "임의 선택"이 아니라 "기준 문서 우선순위 + 팀 확인 대기"로 다뤄서, 나중에 누가 봐도 왜 이렇게 구현했는지 추적 가능하다.

**단점 및 위험 요소**
- lost-items/admin은 아직 모킹이 없어서, 그쪽 화면 개발은 이 구조를 그대로 못 쓰고 별도로 착수해야 한다.
- 날짜 계산(`festivalStatus`, `dday`)이 실제 `new Date()`에 의존해서, 시스템 시간을 고정하지 않으면 스냅샷성 테스트 결과가 매일 바뀐다 — Playwright 도입 시 추가 작업 필요.
- 검색 매칭 로직이 단순 `includes()`라 실제 검색엔진 동작(랭킹, 형태소 분석)까지는 검증하지 못한다 — UI 분기 확인용으로 범위를 한정했다.
- 문서 간 불일치로 팀 확인 대기 중인 항목(`FESTIVAL_INVALID_LIMIT` 범위 등)이 남아있어, 확정 전까지는 그 부분에 한해 실제 API와 다르게 동작할 수 있다.

  있었다. **mock 응답·타입 선언에서는 아직 필드를 지우지 않았다** — 화면이 안 쓰니 동작에는

  `README.md`, `CODE_GUIDE.md`, `features/festivals/types.ts`의 해당 서술은 이번에 갱신했다.
- **`FESTIVAL_INVALID_LIMIT` 범위는 여전히 미확정이다** — 위 소단원의 서술이 지금도 정확하다.
- **`festivals.ts`의 `VALID_SORT`가 `['LATEST', 'UPCOMING', 'POPULAR']`로 명세서의 호출
  예시를 넓게 받아주고 있는데, 실제 프론트가 쓰는 `FestivalSort` 타입은 `LATEST`/`UPCOMING`

  값이라 잘못된 건 아니지만, "명세서에 있던 값과 프론트가 실제로 쓰는 값이 다를 수 있다"는
  예시로 남겨둔다.
