# Issue-Branch — 이슈 등록 + 작업 브랜치 생성

`/issue`로 이슈 문서를 만들고, GitHub에 등록해 **실제 이슈 번호**를 받은 뒤,
저장소 브랜치 관례대로 작업 브랜치를 만들어 전환하는 통합 커맨드.

## 실행 절차

### 1단계: 이슈 작성 (/issue 규칙 그대로)

`.claude/commands/issue.md`(Issue Mode) 규칙을 그대로 따른다:

- 타입 자동 판단(버그 / 기능 / 리팩토링 / 설정 / 문서), 애매하면 짧게 질문
- 제목: `이모지 [타입] 설명` — 한글로 쓴다. 본문은 해당 템플릿, 굵게 강조 금지
- `.issues/[YYYYMMDD]_[타입]_[간단한설명].md`로 저장

### 2단계: GitHub 등록 → 이슈 번호 확보

```bash
gh issue create \
  --title "<제목>" \
  --body "<본문(제목 줄 제외)>" \
  --label "type: <fix|feat|refactor|chore|docs>" \
  --label "작업전"
```

출력 URL 끝의 번호가 **이슈 번호**다. 등록 실패(네트워크·권한) 시 파일만 남기고
사용자에게 알린 뒤 중단한다 — 번호 없이 브랜치를 만들지 않는다.

### 3단계: 작업 브랜치 생성·전환

브랜치 관례: `<타입>_<이슈번호>_<슬러그>` (예: `fix_31_로그인_시_500_에러`)

- **타입**: 2단계에서 붙인 `type:` 라벨의 값 (`fix` / `feat` / `refactor` / `chore` / `docs`)
- **번호**: 2단계에서 받은 이슈 번호
- **슬러그**: 이슈 제목에서 이모지와 `[태그]`를 제거한 뒤, 한글·영문소문자·숫자만 남기고
  나머지는 `_`로 연결. 영문 대문자는 소문자로 내린다

  `❗ [버그] 로그인 시 500 에러` → `로그인_시_500_에러`

**반드시 `develop`에서 분기합니다.**

```bash
git switch develop && git pull
git switch -c "<브랜치명>"
```

이슈 등록 직후 ISSUE-HELPER 봇이 이슈에 브랜치명을 댓글로 답니다.
**봇 제안과 다르면 봇 쪽을 따릅니다** — 봇 형식이 워크플로우의 기준입니다.

### 4단계: 보고 후 그 브랜치에서 작업 계속

- 이슈 URL·번호 · `.issues/` 파일 경로 · 브랜치명을 표로 출력
- 이후 커밋 메시지는 `<이슈 제목> : <타입> : <설명> <이슈 URL>` 형식을 쓴다

## 주의

- push 금지 · Co-Authored-By 금지 — 커밋은 사용자가 요청할 때만
- 이슈 본문에 코드·구현 방법 쓰지 않음(Issue Mode 규칙)
- `gh` 미인증이면 `gh auth status` 안내 후 중단
