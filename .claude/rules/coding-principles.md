# 작업 원칙

에이전트가 이 저장소에서 코드를 만질 때의 판단 기준입니다.
아래 사례는 전부 **이 프로젝트에서 실제로 발생한 것**이고, 그래서 이 규칙이 있습니다.

## 이 파일이 저장소에 있는 이유

팀원마다 쓰는 도구와 개인 설정이 다릅니다. 누구는 Claude Code, 누구는 Codex,
누구는 개인 전역 설정에 자기 규칙을 잔뜩 얹어 씁니다. 그 규율이 개인 환경에만 있으면
**같은 저장소인데 사람마다 에이전트가 다르게 행동합니다.**

그래서 기준을 저장소에 둡니다. 어떤 도구로 열든, 개인 설정이 있든 없든 같은 원칙이
걸리게 하는 것이 목적입니다.

> 이 원칙은 속도보다 신중함 쪽으로 기울어 있습니다. 사소한 작업에는 판단해서 적용하세요.

---

## 1. 가정을 말하고 시작한다

**추측하지 않는다. 헷갈리는 걸 감추지 않는다. 트레이드오프를 드러낸다.**

- 가정은 명시한다. 확신이 없으면 묻는다
- 해석이 여러 개면 전부 제시한다 — 조용히 하나 고르지 않는다
- 더 단순한 방법이 있으면 말한다. 필요하면 반대한다
- 근거가 남의 리포트·블로그·전언이면, 그걸로 설계를 좁히기 전에 직접 확인한다

**이 프로젝트에서 실제로**

브랜치 슬러그에서 한글을 버리는 설계를 했다. 근거는 "한글 브랜치명은 PR 생성 시
`422 Validation Failed`"라는 다른 팀의 이슈 리포트 하나였다. 그 결과
`로그인 시 500 에러` → `fix_31_500` 같은 무의미한 이름이 나왔고, 이를 감수하려고
"제목은 영문으로" 규칙을 템플릿 5개와 봇 가이드에 심었다.

실제로 찔러보니 push·PR 생성·Actions·`gh` 전부 정상이었다. 그 리포트 본문에도
"PowerShell 인코딩 문제 가능성"이라고 적혀 있었다 — 우리 경로와 무관한 클라이언트 버그였다.
잘못된 전제 위에 쌓은 규칙을 전부 되돌렸다.

## 2. 최소한으로 만든다

**문제를 푸는 최소한의 코드. 추측으로 만들지 않는다.**

- 요청받지 않은 기능은 넣지 않는다
- 한 번 쓰는 코드에 추상화를 만들지 않는다
- 요청받지 않은 "유연성"·"설정 가능성"을 넣지 않는다
- 일어날 수 없는 상황에 에러 처리를 넣지 않는다
- 200줄을 썼는데 50줄로 되면 다시 쓴다

스스로 물어본다: "시니어가 이걸 보고 과하다고 할까?" 그렇다면 줄인다.

## 3. 외과적으로 바꾼다

**건드려야 하는 것만 건드린다. 자기가 만든 것만 치운다.**

- 옆에 있는 코드·주석·포맷을 "개선"하지 않는다
- 망가지지 않은 것을 리팩터링하지 않는다
- 자기 취향과 달라도 기존 스타일에 맞춘다
- 관련 없는 죽은 코드를 발견하면 **말만 하고 지우지 않는다**
- 내 변경 때문에 안 쓰이게 된 import·변수·함수는 치운다

판정 기준: **바뀐 모든 줄이 요청과 직접 이어져야 한다.**

**이 프로젝트에서 실제로**

커맨드 파일의 예시를 정규식으로 일괄 치환하다 마크다운 테이블의 앞 컬럼
(`| 1 | abc1234 |`)까지 삼켰다. 패턴이 줄 시작에 앵커돼 있어 의도한 범위를 넘어갔다.
원본과 대조해 복구했다.

되돌리기 어려운 작업(`reset --hard`, `rebase`, 히스토리 재작성)은 백업 브랜치를 먼저 만들고,
끝난 뒤 트리 해시를 대조한다. 스크립트에 쓰는 플래그가 그 명령에 **실제로 존재하는지**
확인한다 — `git cherry-pick -q`(없는 플래그)를 `reset --hard`와 함께 써서 커밋 12개를 날린 적이 있다.

## 4. 검증 기준을 먼저 세운다

**성공 조건을 정의하고, 확인될 때까지 돈다.**

작업을 검증 가능한 목표로 바꾼다.

- "검증 추가" → "잘못된 입력 테스트를 쓰고, 통과시킨다"
- "버그 수정" → "재현하는 테스트를 쓰고, 통과시킨다"
- "리팩터링" → "전후로 테스트가 통과하는지 확인한다"

여러 단계면 짧은 계획을 먼저 말한다.

```
1. [단계] → 확인: [무엇으로]
2. [단계] → 확인: [무엇으로]
```

**검증 통과가 곧 완료는 아니다.** 검사가 잡도록 설계된 것만 잡는다.

**이 프로젝트에서 실제로**

커밋 형식을 바꾼 뒤 `grep -E "_#|#숫자"` 로 잔존을 확인했다. 0건이 나와 통과 처리했는데,
같은 파일 안에 상충하는 두 형식이 공존하고 있었다. `#44`, `<type>` 같은 실제 예시는
패턴에 안 걸렸다. **고치기 전보다 나쁜 상태**였다 — 파일이 두 형식을 동시에 문서화하게 됐기 때문이다.

같은 유형을 이후 6개 파일에서 반복해 발견했다. 일괄 치환 후에는 grep이 통과해도
**파일을 처음부터 끝까지 다시 읽는다.** 특히 예시·표·코드블록 안을 본다 —
산문보다 예시가 늦게 갱신된다.

## 5. 같은 규칙을 두 곳에 적지 않는다

**형식·규칙은 한 곳에만 기술하고 나머지는 가리킨다.**

규칙을 적기 전에 "이미 어디에 적혀 있나"를 먼저 찾는다. 있으면 복사하지 말고 링크한다.
도구가 달라 복사가 불가피하면(레포가 다른 경우) 원본 위치와 동기화 의무를 양쪽에 명시한다.

**이 프로젝트에서 실제로**

커밋 형식 하나가 다섯 곳에 흩어져 있었다 — 봇 스크립트 기본값, `version.yml`,
`commit.md`, `issue-branch.md`, `TEAM-CONVENTIONS.md`. 형식을 두 번 바꾸는 동안
매번 일부만 갱신돼 서로 모순됐다. `report.md`는 산출물이 gitignore된다고 적었는데
`cr.md`는 추적 대상이라고 적고 있었다.

그래서 Codex 지원을 붙일 때는 스킬이 워크플로우를 복사하는 대신 원본 파일을
가리키게 했다. 커맨드를 고치면 양쪽에 동시에 반영된다.

---

**이 원칙이 작동하고 있다면:** diff에 불필요한 변경이 줄고, 과하게 만들어 다시 쓰는 일이
줄고, 질문이 실수 뒤가 아니라 구현 전에 나온다.

# 코드 규약

위 다섯 가지는 판단 기준이다. 아래는 이 스택(Next.js · React · TypeScript · Tailwind CSS 4)
에서의 구체적 표기 규칙이다. 스택이 바뀌면 아래만 바뀐다.

## 폭은 유동으로, 높이는 시안 값으로

[`DESIGN.md`](./DESIGN.md)는 1440 프레임 위에 좌표로 그려진 문서다. **그 프레임은 구상이지
계약이 아니다** — 실제 사용자는 375도 쓰고 2560도 쓴다. 시안의 픽셀은 비율과 위계의 근거이지
코드에 못박을 값이 아니다.

| 종류 | 표기 | 이유 |
| --- | --- | --- |
| 색·타이포·radius·그림자 | 토큰 클래스<br>`bg-primary` `text-entity-name` `rounded-card` | 값이 바뀌면 한 곳만 고친다. hex 인라인 금지 (DESIGN.md Iteration Guide 5) |
| **레이아웃 폭**<br>(컨테이너·그리드·패널·카드) | **유동**<br>`w-full` · `max-w-[…]` · `grid-cols-2 lg:grid-cols-5` | 화면 폭은 우리가 정하는 값이 아니다. 시안의 폭은 "몇 열인지"·"어떤 비율인지"의 근거로만 쓴다 |
| **컴포넌트 높이·아이콘 크기** | 리터럴<br>`h-[48px]` `size-[28px]` | 버튼 높이 48은 화면 폭과 무관하다. 시안 값을 그대로 쓴다 |
| 여백·간격 | 스케일 숫자<br>`p-8` `gap-6` `px-20` | DESIGN.md의 spacing 10종(4·8·12·16·20·24·32·40·64·80)이 Tailwind 기본 4px 스케일과 정확히 일치한다 |

**폭을 고정하지 않는다.** 다만 "유동"이 `w-full`을 뜻하지는 않는다.

| 상황 | 쓸 것 |
| --- | --- |
| 부모 폭을 그대로 채워야 함 (그리드 칸, 컨테이너 자식) | `w-full` |
| 고유 크기가 있고 좁을 때만 줄어야 함 (검색창, 카드, 버튼) | `w-[320px] max-w-full` |
| 내용만큼만 (칩, 뱃지) | 폭 지정 없음 + `min-w-[…]` |

**`w-full max-w-[320px]`은 함정이다.** 부모가 내용에 맞춰 줄어드는 자리
(flex 행의 auto 아이템, `items-start`인 flex 열의 자식, inline 래퍼)에서는 `100%`가 기준을
잃고 내용 폭으로 풀려 요소가 글자 크기로 붕괴한다. `max-w-full`도 같은 이유로 무력해진다.
**부모가 shrink-to-fit이면 자식의 `%`는 기준이 없다** — 자식에 고유 폭을 주거나, 부모에
확정 폭을 줘라.

**이 프로젝트에서 실제로**

디자인 시스템을 처음 옮길 때 `Container`를 `max-w-[1440px] px-20`으로, 검색 pill을
`w-[320px]`로, 색 견본 그리드를 `grid-cols-6`으로 박았다. 시안과 글자가 같아 대조는 편했지만
2560 모니터에서는 양쪽이 비고 좁은 화면에서는 넘쳤다. 코드 전체의 브레이크포인트가 **0개**
였다. 시안 충실도를 위해 쓴 리터럴이 곧 해상도 잠금이었다.

디자인은 디자인일 뿐이고, 우리가 만드는 것은 웹사이트다.

## 조건부 렌더는 삼중연산자로 쓴다

JSX의 `&&`는 좌변이 `0`이나 `NaN`이면 **그 값을 그대로 화면에 그린다.**
(`null`·`undefined`·`false`·`""`는 그리지 않는다.) 값의 타입에 따라 동작이 갈리는 패턴을
쓰지 않는다.

```jsx
{items.length && <List />}                     // ✗ 0이면 화면에 "0"이 찍힌다
{items.length ? <List /> : null}               // ○

{href && <Link href={href}>{label}</Link>}     // ✗
{href ? <Link href={href}>{label}</Link>
      : <span>{label}</span>}                  // ○
```

**특히 링크·라우팅 자리에 적용한다.** 양쪽을 명시하면 "링크가 아닐 때 무엇이 되는가"를
빼먹을 수 없다.

**이 프로젝트에서 실제로**

Footer 링크 10개 중 MVP에 실제 화면이 있는 것은 축제·아티스트·분실물 3개뿐이다. 나머지
7개는 `<span>`으로 둬서 데모 중 404가 나지 않게 한다. `&&`로 썼다면 그 7개가 조용히 사라져
시안과 어긋나고, 사라진 이유도 코드에 남지 않는다.

## CSS Module을 기본으로 쓰지 않는다

스타일은 Tailwind 하나로 간다. 스타일 시스템이 둘이 되면 새 파일마다 "이건 어디에 쓰지"
판단이 매번 붙는다.

- 디자인 토큰은 선택지가 없다 — `@theme`가 Tailwind 4의 토큰 메커니즘이고, 타이포 토큰 하나에
  크기·굵기·행간을 묶는 것은 CSS Module로 못 한다
- 컴포넌트가 작으면(버튼·뱃지·칩) 중첩 셀렉터도 키프레임도 없다

**CSS Module이 이기는 자리**: 키프레임과 상태 조합이 얽히는 애니메이션(히어로 캐러셀 전환),
클래스 문자열이 한 줄 200자를 넘는 컴포넌트, 제어할 수 없는 서드파티 마크업.
그때 **그 파일 하나만** 모듈로 만든다. 미리 규칙을 세우지 않는다.
